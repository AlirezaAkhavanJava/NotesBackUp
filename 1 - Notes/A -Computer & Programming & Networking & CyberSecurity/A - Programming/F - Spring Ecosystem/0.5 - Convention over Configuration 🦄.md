
**Convention over Configuration (CoC)** is a software design principle that reduces the need for explicit configuration by relying on sensible defaults (conventions).

Instead of forcing developers to specify every single detail, the framework assumes "standard" choices and only requires configuration when you deviate from those standards.

> Spring requires explicit configuration, while Spring Boot adds strong conventions and auto-configuration on top of Spring.

---

>“Convention over configuration” (CoC) means the framework assumes sensible defaults for how things should work, so you don’t have to manually configure every little detail. You just follow the framework’s conventions (like naming your classes or files in a certain way), and it “just works.”

Your focus stays on your business logic rather than boilerplate setup.

For example, in Spring Boot, if you name a class `UserRepository` and put it in the right package, Spring automatically wires it up—you don’t have to explicitly configure it.

It’s basically the framework saying: _“If you do things my way, I’ll take care of the plumbing.”_

### Example in Java / Spring:

- **Without CoC**: You would have to specify in XML that a class `UserService` is a service, map every field to DB column names, etc.
    
- **With CoC**:
    
    - Spring automatically detects `@Service`, `@Controller`, etc. based on class annotations.
        
    - Hibernate/JPA assumes a field named `id` is the primary key unless told otherwise.
        
    - `application.properties` has sensible defaults (e.g., server runs on port `8080` if not configured).

### Benefits:

1. **Less boilerplate** → Developers focus on business logic.
2. **Consistency** → Standardized naming and structure across projects.
3. **Flexibility** → You can still override defaults if needed.
