
Java 26 (and possibly Java 27, given today's date) falls after my reliable knowledge cutoff, and Java's release cadence means there could be a version I don't have solid details on yet. Let me check current information rather than guess.# Java 26 — New Features (Non-LTS Release)

Java 26 was released **March 17, 2026** — the first non-LTS release since Java 25. Since Java follows a strict six-month cadence (March/September), Java 26 is a **short-term** release — most production teams (especially anyone on a conservative upgrade cycle) will likely stay on Java 25 (LTS) rather than adopt Java 26 directly, with the next LTS (Java 29) still to come. Still, it's worth knowing what's in it, especially since several features continue directly from what you already know from Java 21/25.

Ten JEPs total: five finalized, four in preview, one incubating.

---

## 1. JEP 500 — Prepare to Make Final Mean Final — finalized

**Definition:** tightens the guarantee behind the `final` keyword on fields — historically, Java allowed certain narrow escape hatches (mainly via deep reflection) to modify a `final` field after construction, which technically violated what "final" is supposed to promise. This JEP is a **preparatory** step, warning about and starting to close those loopholes ahead of a future release that will fully enforce it.

```java
final class Config {
    final String name;
    Config(String name) { this.name = name; }
}
```

**Problem it solves:** `final` is supposed to mean "this value can never change after construction" — but reflection-based tricks (`Field.setAccessible(true)` + `Field.set()`) could historically bypass that in some cases. This JEP begins the process of making `final` an actually-enforced guarantee, not just a convention.

**Relevance to you:** purely forward-looking hardening — doesn't change how you write normal code using `final`, but signals that reflection-based workarounds you might see in older codebases will stop working in a future JDK.

## 2. JEP 504 — Remove the Applet API — finalized (removal)

**Definition:** completes the removal process for `java.applet`, which was marked "deprecated for removal" back in Java 17 (as covered in that tutorial). The package is now **gone entirely**.

**Relevance:** purely historical cleanup — confirms applets are fully retired from the JDK.

---

## 3. JEP 516 — Ahead-of-Time Object Caching with Any GC — finalized

**Definition:** extends AOT (Ahead-of-Time) object caching — a startup/warmup performance feature — so it works with **any** garbage collector, including **ZGC** (the low-pause-time collector covered in the Java 21/25 tutorials), not just the older Serial/Parallel/G1 collectors it was previously limited to.

**Problem it solves:** the AOT cache previously stored heap objects in a format tied to the internal layout of specific collectors (Serial, Parallel, G1) — meaning if you wanted ZGC's low-pause benefits (from the Java 21 tutorial), you couldn't also benefit from AOT caching's faster startup. This JEP stores cached objects in a GC-**neutral** format, letting you combine ZGC's low pause times with AOT's faster startup — previously mutually exclusive benefits.

**Relevance:** JVM-level performance improvement, automatic — no code changes needed, directly relevant if you ever tune a Spring Boot app's startup time in production.

---

## 4. JEP 517 — HTTP/3 for the HTTP Client API — finalized

**Definition:** adds **HTTP/3** protocol support to `java.net.http.HttpClient` — the modern HTTP client covered in the networking section of the Java API reference tutorial.

```java
HttpClient client = HttpClient.newBuilder()
    .version(HttpClient.Version.HTTP_3) // new in Java 26
    .build();

HttpRequest request = HttpRequest.newBuilder()
    .uri(URI.create("https://example.com"))
    .build();

HttpResponse<String> response = client.send(request, HttpResponse.BodyHandlers.ofString());
```

**Problem it solves:** `HttpClient` previously supported only HTTP/1.1 and HTTP/2 (as noted when it was introduced back in Java 11). HTTP/3 — standardized in 2022, built on the QUIC transport protocol instead of TCP — offers genuine improvements in connection setup speed and resilience to network changes (especially valuable for mobile/unreliable connections). With **over a third of web servers now supporting HTTP/3**, Java's HTTP client finally catches up to what a growing share of the modern web actually speaks.

**Relevance:** directly useful if your Spring Boot application makes outbound HTTP calls to third-party APIs — some of which may now be reachable over HTTP/3 with genuine latency benefits.

---

## 5. JEP 522 — G1 GC: Improve Throughput by Reducing Synchronization — finalized

**Definition:** an internal optimization to the **G1** garbage collector (the JVM's long-standing default GC) that reduces the amount of internal thread synchronization needed during garbage collection, improving overall throughput.

**Problem it solves:** this connects directly to the concurrency tutorials' discussion of synchronization overhead and context-switching cost — G1's internal collection machinery itself was paying unnecessary synchronization costs; reducing that means more of your CPU's actual capacity goes toward running your application rather than GC bookkeeping.

**Relevance:** automatic, JVM-internal — no code changes, but genuinely relevant since **G1 is set to become the default GC across all environments** (mentioned in the search results, via the upcoming JEP 523), meaning most Spring Boot applications benefit from this without any configuration at all.

## Preview Features (not yet finalized — API may still change)

### 6. JEP 524 — PEM Encodings of Cryptographic Objects (Second Preview)

Continues from the **first preview** you saw in the Java 25 tutorial (JEP 470) — refined based on feedback, still not finalized.

```java
PEMEncoder encoder = PEMEncoder.of();
String pem = encoder.encodeToString(someKey); // API refined from the Java 25 preview, still not final
```

**Status:** second preview round — the API shape has already changed once since Java 25; expect it to potentially shift again before finalizing.

### 7. JEP 525 — Structured Concurrency (Sixth Preview)

Continues from the **fifth preview** in Java 25 (which itself continued from Java 21's original preview) — now with **timeout handling and joiner refinements**.

```java
try (var scope = StructuredTaskScope.open(
        StructuredTaskScope.Joiner.<String>awaitAllSuccessfulOrThrow())) {
    var user = scope.fork(() -> fetchUser());
    var order = scope.fork(() -> fetchOrder());
    scope.join();
    // new: custom joiners can now receive a timeout callback for more flexible error handling
}
```

**What's new in this round specifically:** a **timeout callback for custom joiners** — letting you define exactly what happens when a group of structured subtasks times out, rather than only having generic cancellation behavior.

**Status:** this is genuinely the longest-running preview feature you've tracked across this whole conversation — six preview rounds since Java 21, still actively evolving. This is a real, concrete example of the "preview features can still change" caution repeated throughout the concurrency tutorials — worth treating as a moving target rather than something to build production code around yet.

### 8. JEP 526 — Lazy Constants (Second Preview)

**Definition:** a new API for declaring constants that are **computed only when first accessed** ("lazily"), rather than eagerly at class-loading time — while still guaranteeing the value never changes once computed (a "stable" value).

```java
// Conceptual illustration — exact API still evolving across preview rounds
StableValue<Config> config = StableValue.ofLazy(() -> loadExpensiveConfig());
// loadExpensiveConfig() only actually runs the FIRST time config.get() is called
```

**Problem it solves:** a traditional `static final` field is computed **eagerly**, the moment its class loads — even if that computation is expensive and the value might never actually be used in a given run. Lazy Constants let you defer that cost until (and unless) the value is genuinely needed, while still keeping the "never changes once set" guarantee `final` normally provides — directly connecting to JEP 500's theme of strengthening what "final"/constant actually means.

**New in this round:** a `ofLazy()` factory method for creating **stable collections** — lazily-initialized, immutable collection wrappers.

**Status:** second preview — refined from the Java 25 tutorial's first preview appearance.

### 9. JEP 530 — Primitive Types in Patterns, `instanceof`, and `switch` (Fourth Preview)

Continues directly from the **third preview** you saw in the Java 25 tutorial (JEP 507) — same feature, fourth round of refinement.

```java
Object obj = 42;
String result = switch (obj) {
    case int i when i > 100 -> "Big int";
    case int i -> "Small int";
    default -> "Other";
};
```

**Status:** fourth preview round — this feature has now been refined across four consecutive releases (Java 23 through 26), suggesting it's converging toward finalization but genuinely still not there yet.

## Incubator Feature

### 10. JEP 529 — Vector API (Eleventh Incubator)

**Definition:** an API for expressing **vector computations** — operations that process multiple data values simultaneously using CPU-level SIMD (Single Instruction, Multiple Data) instructions — that reliably compile down to optimal hardware vector instructions across different CPU architectures at runtime.

```java
// Conceptual illustration — the Vector API lets you express "do this math on 8 numbers at once"
// in a way that compiles to genuine SIMD CPU instructions, rather than 8 separate operations
```

**Problem it solves:** modern CPUs can perform the same arithmetic operation on **multiple values simultaneously** in a single instruction (SIMD) — genuinely useful for numeric-heavy workloads (image processing, machine learning, scientific computing). Without a dedicated API, Java code couldn't reliably access this hardware capability in a portable way; the JIT compiler's own automatic vectorization is limited and unpredictable. The Vector API lets you **explicitly** express vectorized computation in portable Java code.

**Status:** this is genuinely remarkable for how long it's been incubating — **eleventh** round, spanning **years** of JDK releases (since Java 16). This is the most extreme real example in this entire conversation of "incubator/preview means genuinely still evolving" — even longer-running than structured concurrency's six rounds. If you ever need this for numeric performance work, treat it as still fundamentally experimental.

## Notable smaller changes (non-JEP)

- **`InitialRAMPercentage` default changed from 1.5625% to 0%** — the JVM now relies more heavily on automatic ergonomics to size the initial heap appropriately for modern hardware, rather than a fixed legacy default dating back to 2007.
- **Removal of `AlwaysActAsServerClassMachine`/`NeverActAsServerClassMachine`/`AggressiveHeap` flags** — cleanup of old, low-transparency JVM tuning flags, made largely obsolete now that G1 is becoming the universal default GC.
- **Unicode 17.0 and CLDR v48 support** — updated international text/locale data.
- **HPKE (Hybrid Public Key Encryption)** and **post-quantum-ready JAR signing** — security modernization, connecting to the KEM (Java 21) and KDF (Java 25) cryptography APIs from the earlier tutorials.
