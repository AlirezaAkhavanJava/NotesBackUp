
## `.git/info/exclude` — Deep Dive

---

## Core Intuition First

You already know `.gitignore` as a file sitting in the working directory, committed and shared with everyone who clones the repo. `.git/info/exclude` solves a slightly different problem: **what if you want to ignore a file, but _only for yourself_, without that ignore rule being visible to (or imposed on) anyone else?**

> **Mental model:** `.gitignore` is a _shared, committed_ ignore list. `.git/info/exclude` is a _private, local-only_ ignore list — same exact syntax, same exact matching behavior, but it never leaves your machine because it lives **inside** `.git/`, which itself is never tracked by Git (Git doesn't track its own internals).

---

## Where It Lives

```
.git/info/exclude
```

Every repository has this file already, created automatically by `git init`/`git clone` — usually with some boilerplate comments, sometimes empty. You just open and edit it directly:

```bash
nano /mnt/hdd/Home/Programming\ Files/Git/webflyx/.git/info/exclude
```

---

## Why `.git/info/exclude` Exists — The Specific Problem It Solves

`.gitignore` is committed, meaning it's **part of the project** — everyone who clones the repo gets your ignore rules too, and if you change `.gitignore`, that change shows up as a diff everyone sees.

But some ignore needs are **personal, not project-wide**:

|Scenario|Why it shouldn't go in `.gitignore`|
|---|---|
|You use a personal scratch file (`notes-to-self.txt`) inside the repo, nobody else uses this|Not relevant to teammates — cluttering the shared `.gitignore` with your personal habits|
|You use a specific editor/IDE teammates don't (e.g. a less common plugin's config files)|`.gitignore` should reflect the project's _actual_ tooling conventions, not your individual setup|
|You're experimenting with ignoring something temporarily, not sure if it should be permanent|Don't want to create a commit/diff for something you might revert in an hour|
|You don't have write access to influence `.gitignore` conventions (e.g. contributing to someone else's open-source project)|You can still have local, personal ignores without needing permission or opening a PR just to add your own convenience rule|

---

## Syntax — Identical to `.gitignore`

Same pattern language exactly — everything covered earlier applies unchanged:

```
# .git/info/exclude
notes-to-self.txt
*.scratch
my-local-experiment/
```

---

## The Precedence/Combination Rule

Git actually checks **multiple** ignore sources, combined together, in this order of precedence (later ones can override earlier ones via negation):

1. `.git/info/exclude` (local, highest-priority local override)
2. `.gitignore` files (root + any in subdirectories, committed and shared)
3. Global ignore file (`core.excludesfile`, e.g. `~/.gitignore_global`, covered earlier — machine-wide, across _all_ repos)

All of them get merged into one effective ignore list for that repo. `git check-ignore -v <file>` (the debug command from earlier) will actually tell you **which specific file** a given ignore rule came from — useful when you're not sure if a pattern is coming from `.gitignore` or `.git/info/exclude`.

```bash
git check-ignore -v notes-to-self.txt
```

```
.git/info/exclude:3:notes-to-self.txt    notes-to-self.txt
```

---

## Why It's Never Committed — The Mechanical Reason

This connects directly to something from much earlier: `.git/` is the repository's internal database — objects, refs, config, HEAD. Git never tracks its own internals as content inside those same internals; that would be a strange kind of self-reference. `.git/info/exclude` lives there specifically _because_ it's meant to be local-machine-only, by the same logic that `.git/config` (your remotes, your `user.name`) is also local-only and never pushed anywhere.

**This also means:** `.git/info/exclude` doesn't survive a fresh clone. If you clone the repo again on another machine, you get a brand new empty `.git/info/exclude` — your personal rules don't travel with you automatically (unlike `.gitignore`, which is baked into the committed project and comes with every clone).

---

## `.gitignore` vs `.git/info/exclude` vs Global Excludes — Full Comparison

||`.gitignore`|`.git/info/exclude`|Global (`core.excludesfile`)|
|---|---|---|---|
|Committed/shared?|Yes|No — local only|No — local only|
|Scope|This project, for everyone|This **clone**, for you only|Every repo on your machine|
|Survives re-clone?|Yes (it's part of the repo)|No — stays with this one `.git` folder|Yes (it's outside any repo, in your home dir)|
|Typical use|Build artifacts, deps, secrets — things that are objectively project-irrelevant|Personal scratch files, local experiments, your own temporary needs|Editor/OS junk that follows _you_ everywhere (`.DS_Store`, `.idea/`)|

---

## When to Use Which — Decision Rule

```
Is this ignore rule relevant to EVERYONE on the project (build output, deps, secrets)?
  → .gitignore (commit it)

Is this ignore rule about YOUR editor/OS, and would apply to every repo you touch?
  → global core.excludesfile

Is this ignore rule specific to just this one clone, just for you, not worth a commit/diff?
  → .git/info/exclude
```

---

**One-line definition to remember:**

> `.git/info/exclude` is a personal, uncommitted, per-clone ignore file — same syntax as `.gitignore`, but invisible to collaborators and left behind if you ever re-clone, making it the right place for ignore rules that are about _you_, not the project.
