
`@GeneratedValue` tells JPA that you won't assign the primary key yourself. Something else creates it: the database, a sequence, or Hibernate. You put it next to `@Id`, and when you call `save()` on a new entity, the id appears. The annotation has only two parameters, but the strategy you choose changes your insert performance, your batching, your migrations, and what your ids look like to the outside world.

So this lesson is mostly a decision lesson. First the parameters, then each strategy and how it behaves, then which database gets which, and finally what a production setup looks like. I'm assuming you know entity basics (from your entity design lessons) and Flyway/DDL (from your DDL lesson), so I'll build on those.

## The two parameters

```java
@Id
@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "order_seq_gen")
private Long id;
```

- `strategy` is a `GenerationType`: `AUTO` (default), `IDENTITY`, `SEQUENCE`, `TABLE`, `UUID`.
- `generator` is optional. It's the name of a generator definition, usually `@SequenceGenerator` or `@TableGenerator`, that gives you control over the sequence name and size. If you leave it out, Hibernate picks defaults.

That's the whole annotation. The detail lives in the generator annotations.

## The strategies, one by one

### IDENTITY

The database fills the id when the row is inserted.

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

PostgreSQL DDL for it:

```sql
CREATE TABLE users (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    email TEXT NOT NULL
);
```

Here is the catch. Hibernate doesn't know the id until the INSERT has run. So on `save()` it must execute the INSERT _immediately_, not at flush time. That has one big consequence: **JDBC batch inserts are disabled** for IDENTITY entities. Insert 1,000 rows and you get 1,000 separate round trips.

Use it when inserts are low volume, or the database gives you nothing better.

### SEQUENCE

A database sequence hands out numbers. Hibernate asks the sequence for ids _before_ the insert, so it can batch.

```java
@Entity
public class Orders {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "orders_seq_gen")
    @SequenceGenerator(
        name = "orders_seq_gen",       // name used by @GeneratedValue
        sequenceName = "orders_seq",   // real sequence in the database
        allocationSize = 50            // ids reserved per database call
    )
    private Long id;
}
```

Line by line:

- `name` is only a label inside your Java code. It links the two annotations.
- `sequenceName` is the actual sequence object in PostgreSQL.
- `allocationSize` (default **50**) is the important one. Hibernate calls `nextval` once, then hands out 50 ids from memory. That's 1 database call per 50 inserts.
- `initialValue` (default 1) is where the sequence starts. `catalog` and `schema` place it in a specific schema, which connects to your schema lesson.

The matching DDL must agree with `allocationSize`:

```sql
CREATE SEQUENCE orders_seq START WITH 1 INCREMENT BY 50;
```

How the numbers work (Hibernate's "pooled" optimizer): `nextval` returns 51. Hibernate treats that as the top of a range and uses 2…51 itself. The next `nextval` returns 101, and so on. If `INCREMENT BY` and `allocationSize` don't match, Hibernate can hand out duplicate ids or log a mismatch warning. Always keep them equal.

What you see in the SQL log: one `select nextval('orders_seq')`, then a burst of inserts that can be batched.

### TABLE

A helper table holds a counter and Hibernate updates it under a lock.

```java
@GeneratedValue(strategy = GenerationType.TABLE, generator = "t_gen")
@TableGenerator(name = "t_gen", table = "id_gen", allocationSize = 50)
```

It works on any database, which is its only advantage. It's slower and creates lock contention. If you're on PostgreSQL or SQLite, you don't need it.

### UUID

Added in JPA 3.1. Hibernate generates the id in the application, no database round trip at all.

```java
@Id
@GeneratedValue(strategy = GenerationType.UUID)
private UUID id;
```

```sql
CREATE TABLE users (id UUID PRIMARY KEY, email TEXT NOT NULL);
```

Pros: no database call, batching works, ids can be created before saving, and they don't reveal how many rows you have. Cons: 16 bytes instead of 8, and **random** UUIDs (version 4) scatter inserts across the primary key's B-tree index, which causes page splits and a bigger, slower index on large tables.

The fix is a **time-ordered** UUID. In Hibernate 6.x you can use `@UuidGenerator(style = UuidGenerator.Style.TIME)`. Newer Hibernate 7 also offers a version 7 style. PostgreSQL 18 even has a built-in `uuidv7()` function you can use as a column default. Check which Hibernate version your Spring Boot brings before picking.

### AUTO

You let the provider decide. In Hibernate 6+ with a `Long` id, it generally means a sequence, named after the entity (like `Orders_SEQ`) with `allocationSize` 50. On databases without sequences it falls back to something else. For a `UUID` field it picks UUID generation.

The trouble: the choice depends on dialect and version, and you can't see it in the code. For production, **don't use AUTO**. Write the strategy out.

## Which database gets which strategy

|Database|Best choice|Why|
|---|---|---|
|PostgreSQL|`SEQUENCE` (or `UUID` with time-ordered ids)|Real sequences, fast, batchable. `IDENTITY` also works if you accept no batching.|
|Oracle, SQL Server 2012+|`SEQUENCE`|Native sequences.|
|MySQL / MariaDB|`IDENTITY` (`AUTO_INCREMENT`)|Historically no sequences (MariaDB 10.3+ has them).|
|SQLite|`IDENTITY`|No sequence objects at all. The id is `INTEGER PRIMARY KEY`, which auto-fills, and the community dialect supports identity.|
|H2 (tests)|`SEQUENCE`|Supports it, matches your PostgreSQL setup.|

For SQLite, the entity looks like:

```java
@Id
@GeneratedValue(strategy = GenerationType.IDENTITY)
private Long id;
```

Since you use both PostgreSQL and SQLite: if one entity class must work on both, `IDENTITY` is the common denominator. If PostgreSQL is your real production database, use `SEQUENCE` there and keep SQLite for small local tools.

## Designing it for production

Here's a setup that holds up.

**1. Pick the strategy explicitly, one per entity type.** For PostgreSQL, `SEQUENCE` with a named `@SequenceGenerator`.

**2. Create the sequence in a Flyway migration, not through Hibernate.**

```sql
-- V3__create_orders.sql
CREATE SEQUENCE orders_seq START WITH 1 INCREMENT BY 50;

CREATE TABLE orders (
    id     BIGINT PRIMARY KEY,
    status TEXT NOT NULL
);
```

```properties
spring.jpa.hibernate.ddl-auto=validate
```

With `validate`, Hibernate checks the schema matches your entities and fails at startup if the sequence is wrong. That catches the `allocationSize` mismatch before it becomes duplicate keys.

**3. Turn batching on, since you chose SEQUENCE for exactly this.**

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
```

**4. Use `Long`, not `long`, for the id.** A `null` id is how Spring Data knows an entity is new. A primitive `long` is never null, so Spring Data would think a new entity already exists and do a `merge` (an extra SELECT) instead of a `persist`.

**5. Never set the id yourself on a generated entity.** Passing an entity with a preset id to `save()` triggers the merge path above, and often an error.

**6. Don't expose sequential ids publicly.** `/orders/1`, `/orders/2` lets anyone guess records and count your data. Two options: make the primary key a UUID, or keep a `BIGINT` primary key for joins and add a separate `public_id UUID` column for your API. The second is common because joins stay fast and ids stay hidden.

**7. If other programs insert into the same table with raw SQL, set `allocationSize = 1`** (and `INCREMENT BY 1`). With pooled ids, an outside `nextval` can land inside the range Hibernate is using, causing a duplicate key. If only your app writes, keep 50.

**8. Accept gaps.** Restarts, rollbacks, and pooled ranges all leave holes in the sequence. Ids are unique, not gapless and not strictly time-ordered across several app instances. If you need gapless invoice numbers, generate those separately with business logic. Don't try to get them from `@GeneratedValue`.

**9. Use `BIGINT`/`Long`.** A 32-bit `INT` caps at about 2.1 billion, and sequences burn numbers faster than you expect.

## A related concept: the optimizer

The "pooled" behavior above is called an _optimizer_, and it is what lets one `nextval` serve many inserts. Hibernate also has `pooled-lo` and a few others, but with `@SequenceGenerator` and a matching `INCREMENT BY`, pooled is already what you get. Beyond that, if you need a fully custom id (say, a prefixed code), Hibernate's `@IdGeneratorType` lets you plug in your own generator class.
