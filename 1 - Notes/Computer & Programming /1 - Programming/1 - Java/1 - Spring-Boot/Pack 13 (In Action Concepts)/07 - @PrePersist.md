
# JPA Lifecycle Callbacks: `@PrePersist` and Its Family

## Part 1: What is a lifecycle callback?

A **lifecycle callback** is a method on an entity class that the JPA provider (Hibernate, in most Spring Boot projects) calls automatically at a specific moment in an entity's life: when it is saved, updated, deleted, or loaded.

You never call these methods yourself. You annotate a method, and Hibernate invokes it at the right time.

**Why does it exist?** Entities often need small bits of automatic work. A `createdAt` timestamp should be set the first time a record is saved. An `updatedAt` timestamp should change every time a record is modified. Without callbacks, you would have to remember to set these fields in every service method that touches the entity. Forgetting once would leave the data inconsistent.

**What problem does it solve?** It moves that bookkeeping into the entity, so the rule lives in one place and runs whenever the event happens, regardless of which service or repository did the saving.

**How does it work?** When your code calls `repository.save(task)`, Hibernate goes through a sequence of steps. At certain points in that sequence, it looks for annotated methods on your entity and runs them. Your method then modifies the entity's fields, and Hibernate writes the result to the database.

**How will you use it?** You will use callbacks for timestamps, audit trails, derived values, normalizing input (such as trimming or lowercasing a field before storage), and logging entity events.

## Part 2: `@PrePersist`

### Definition

`@PrePersist` marks a method that Hibernate calls **just before a new entity is inserted into the database** for the first time. "Persist" is JPA's word for "save a new entity." It is triggered by `em.persist(entity)`, or by `repository.save(entity)` when the entity is new.

### The rules for the method

- It must return `void`.
- It must take no parameters.
- It can be `private`, `protected`, package-private, or `public`.
- It must not be `static` or `final`.
- It should not call `EntityManager` operations such as `persist` or `remove` on other entities. Keep it to changing the entity's own state.

### Example 1: Setting creation and update timestamps

```java
import jakarta.persistence.*;
import java.time.Instant;

@Entity
@Table(name = "tasks")
public class Task {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    private Instant updatedAt;

    @PrePersist
    void onCreate() {
        this.createdAt = Instant.now();
        this.updatedAt = this.createdAt;
    }

    @PreUpdate
    void onUpdate() {
        this.updatedAt = Instant.now();
    }

    // getters and setters omitted for brevity
}
```

**What each part does:**

- `@Entity` and `@Table` tell JPA that this class maps to the `tasks` table.
- `@Id` and `@GeneratedValue` make `id` the primary key, generated by the database.
- `@Column(nullable = false, updatable = false)` on `createdAt` means the column cannot be null, and Hibernate will never include it in an `UPDATE` statement. This protects the creation time from being overwritten later.
- `onCreate()` runs before the first `INSERT`. It sets `createdAt` to the current time, then copies that value into `updatedAt` so both start out equal.
- `onUpdate()` is `@PreUpdate`, which we will cover in Part 3. It refreshes `updatedAt` every time the entity changes.

**Usage in a service:**

```java
Task task = new Task();
task.setTitle("Learn JPA callbacks");
taskRepository.save(task);
// At this point, createdAt and updatedAt have been filled in by onCreate().
// You never wrote a line that set them.
```

### Example 2: Normalizing input before it is stored

Callbacks are not only for timestamps. They are useful whenever a field should always be stored in a particular form.

```java
@Entity
public class User {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @PrePersist
    @PreUpdate
    void normalizeEmail() {
        if (email != null) {
            this.email = email.trim().toLowerCase();
        }
    }

    // getters and setters omitted
}
```

Here one method carries two annotations, `@PrePersist` and `@PreUpdate`, so it runs on both insert and update. If a user saves `" Alice@Example.COM "`, the database receives `"alice@example.com"`. The unique constraint on `email` now works correctly, because `Alice@Example.COM` and `alice@example.com` are the same address after normalization.

### A gotcha to remember about `@PrePersist`

Do not rely on the `id` being set inside `@PrePersist`. With `GenerationType.IDENTITY`, the database assigns the id during the insert, so the id is still `null` when your callback runs. If you need the id, use `@PostPersist` instead.

## Part 3: The rest of the callback family

JPA defines seven lifecycle annotations. Each one fires at a different point. Here is the order for a single entity, as a table:

|Annotation|Fires when|Typical use|
|---|---|---|
|`@PostLoad`|After an entity is loaded from the database|Compute transient (non-stored) fields|
|`@PrePersist`|Before a new entity is inserted|Set `createdAt`, default values|
|`@PostPersist`|After a new entity is inserted|Log the new id, publish an event|
|`@PreUpdate`|Before an existing, changed entity is updated|Set `updatedAt`, normalize data|
|`@PostUpdate`|After an update is executed|Log or react to the change|
|`@PreRemove`|Before an entity is deleted|Check or clean up related state|
|`@PostRemove`|After an entity is deleted|Log the deletion|

### `@PreUpdate`

This fires only when Hibernate detects that the entity has changed. If you load a task and save it without changing anything, `@PreUpdate` does not run, because no `UPDATE` is needed. That is why `updatedAt` in Example 1 reflects real changes rather than every save.

### `@PostPersist` example: using the generated id

```java
@Entity
public class Order {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String product;

    @PostPersist
    void afterInsert() {
        System.out.println("Order saved with id = " + id);
    }
}
```

By the time `@PostPersist` runs, the insert has executed and the database has returned the generated id. Printing it here works, where it would have printed `null` inside `@PrePersist`.

In a real application, you would use a logger such as SLF4J instead of `System.out`, but the timing lesson is the same.

### `@PostLoad` example: computing a value that is not stored

```java
@Entity
public class Subscription {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private LocalDate startDate;

    @Transient
    private long daysActive;

    @PostLoad
    void computeDaysActive() {
        this.daysActive = ChronoUnit.DAYS.between(startDate, LocalDate.now());
    }

    // getters omitted
}
```

**What this does:**

- `@Transient` is `jakarta.persistence.Transient`. It tells JPA that `daysActive` is not a database column. Without it, Hibernate would try to create a column for the field.
- `@PostLoad` runs every time a `Subscription` is read from the database. It fills `daysActive` from `startDate`, so the value is always current when you use it.

The value is recalculated on every load, so it is never stale, but it is also never saved.

### `@PreRemove` example: a guard before deletion

```java
@Entity
public class Project {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "project")
    private List<Task> tasks = new ArrayList<>();

    @PreRemove
    void ensureNoTasks() {
        if (!tasks.isEmpty()) {
            throw new IllegalStateException("Cannot delete a project that still has tasks");
        }
    }
}
```

Throwing a runtime exception inside a callback aborts the operation, and the surrounding transaction is rolled back. The delete never reaches the database. Use this for last-chance validation, but keep the main business rules in your service layer, where they are easier to read and test.

## Part 4: Gotchas and good practice

- **Keep callbacks small.** They should set or adjust the entity's own fields. Anything involving other services, network calls, or complex queries belongs in the service layer.
- **Do not call `EntityManager` or repository methods inside callbacks.** Doing so can trigger nested flush behavior and produce confusing errors.
- **Callbacks run inside the transaction.** A thrown exception rolls everything back. That is useful, but it also means slow code in a callback slows the whole transaction.
- **Know that callbacks are a JPA feature, not a Spring feature.** Spring does not run them; Hibernate does. This matters when you debug, because a Spring-level breakpoint will not explain the timing.

## Part 5: The Spring way of doing timestamps

You will meet a more common approach in real Spring Boot projects. Spring Data JPA provides auditing annotations that do what Example 1 does, with less code:

```java
@Entity
@EntityListeners(AuditingEntityListener.class)
public class Task {

    @CreatedDate
    @Column(nullable = false, updatable = false)
    private Instant createdAt;

    @LastModifiedDate
    private Instant updatedAt;

    // ...
}
```

This also requires `@EnableJpaAuditing` on a configuration class. Under the hood, `AuditingEntityListener` is itself a set of JPA callbacks, which is a good reason to understand `@PrePersist` first. Learning the raw callbacks makes it much easier to see what Spring's auditing is doing for you.
