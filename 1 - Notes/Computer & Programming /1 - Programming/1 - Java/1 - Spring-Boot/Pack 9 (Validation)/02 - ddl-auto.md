
# `ddl-auto`: How Much Control Hibernate Has Over Your Schema

**Definition:** `spring.jpa.hibernate.ddl-auto` tells Hibernate what to do with the database schema when the application starts. It is passed to Hibernate as `hibernate.hbm2ddl.auto`. Depending on the value, Hibernate does nothing, checks the schema, modifies it, or rebuilds it from your entity classes.

**Mental model:** The setting is the amount of authority you give Hibernate over the schema at startup.

- `none`: no authority
- `validate`: read-only, can only complain
- `update`: can add things
- `create` / `create-drop`: can destroy and rebuild everything

Compare it to a deploy tool's dry-run vs apply flags. The analogy breaks down because these modes don't form a safe-to-dangerous ladder. `update` looks gentler than `create` but is arguably worse in production, because it fails silently and leaves the schema in a state nobody planned.

## The five values

|Value|What Hibernate does at startup|Data survives?|Realistic use|
|---|---|---|---|
|`none`|Nothing|Yes|Production with Flyway/Liquibase|
|`validate`|Checks that tables, columns, and types match the entities. Throws and aborts startup on mismatch|Yes|Production/staging, as a safety check|
|`update`|Adds missing tables and columns|Yes|Quick local prototyping only|
|`create`|Drops the entity tables, then creates them|**No**|Throwaway dev databases|
|`create-drop`|Same as `create`, and also drops them on shutdown|**No**|Tests|

**The default is surprising.** If you don't set it, Spring Boot uses `create-drop` for an _embedded_ database (H2, HSQLDB, Derby) when no schema manager like Flyway is detected, and `none` otherwise. So an app that "just worked" on H2 will start with no tables the moment you point it at PostgreSQL, because the default silently flipped.

## What each mode produces

Take this entity:

```java
@Entity
@Table(name = "users")
class User {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 50)
    private String name;
}
```

With `create`, Hibernate runs roughly:

```sql
drop table if exists users cascade;
create table users (
    id bigint generated by default as identity,
    name varchar(50) not null,
    primary key (id)
);
```

Line by line:

- `drop table if exists users cascade`: Existing data in this table is gone. This is the step that makes `create` dangerous.
- `varchar(50) not null`: This is where `@Column(length = 50, nullable = false)` has its effect, which is the DDL-only role from the previous lesson.
- `generated by default as identity`: Comes from `GenerationType.IDENTITY`. The exact SQL differs per database dialect.

Now add a field and restart with `update`:

```java
@Column(length = 30)
private String nickname;
```

Hibernate runs only:

```sql
alter table users add column nickname varchar(30);
```

It compared the entity to the existing table, found a missing column, and added it. Existing rows get `NULL` in the new column.

## Why `update` is a trap

`update` only knows how to **add**. It has no concept of history or intent, so these cases go wrong:

1. **Rename a field** (`name` → `fullName`): Hibernate sees a new column `full_name` and adds it. The old `name` column stays, and your data is not copied over. The new column is empty.
2. **Change a length** (`length = 50` → `100`): Nothing happens. The existing column stays `VARCHAR(50)`, so your entity claims 100 while the database enforces 50. This is the drift problem from the last lesson.
3. **Add `nullable = false` to an existing column**: It may fail if rows already contain nulls, or be skipped. Behavior depends on the database and dialect.
4. **Remove a field**: The column stays forever.
5. **No record of what happened**: There's no version number, no review, no way to reproduce the same schema on another machine, and no rollback.

The core problem: a schema is **state with history**, and `update` treats it as something you can recompute from the current code. Data migrations (copying `name` into `full_name`, splitting a column, backfilling defaults) can't be inferred from entities at all.

## `validate`: useful, but narrower than it sounds

`validate` doesn't change anything. It compares entities to the real schema and refuses to start if they disagree:

```
Schema-validation: missing column [nickname] in table [users]
```

```
Schema-validation: wrong column type encountered in column [age] in table [users];
found [varchar (Types#VARCHAR)], but expecting [integer (Types#INTEGER)]
```

What it **does** check: that the tables and columns exist, and that column types are compatible. What it does **not** check: `length`, `nullable`, `unique`, indexes, or foreign-key constraints, and it doesn't care about extra columns in the table that the entity doesn't map.

That means I need to correct something from my last answer. I suggested `validate` as a way to keep the numbers in sync, but it can't catch `VARCHAR(50)` vs `length = 100`. It catches **structural** drift (missing column, wrong type), not **constraint** drift. For constraint drift you need a test that runs against a real database with your real migrations and tries to insert boundary values.

## The setup that real projects use

Let a migration tool own the schema, and let Hibernate only verify it.

```xml
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-core</artifactId>
</dependency>
<!-- Flyway 10+ (Spring Boot 3.3+): database support is a separate module -->
<dependency>
    <groupId>org.flywaydb</groupId>
    <artifactId>flyway-database-postgresql</artifactId>
</dependency>
```

```yaml
# application.yml (shared / production)
spring:
  jpa:
    hibernate:
      ddl-auto: validate
```

```sql
-- src/main/resources/db/migration/V1__create_users.sql
create table users (
    id   bigint generated by default as identity primary key,
    name varchar(50) not null
);
```

```sql
-- src/main/resources/db/migration/V2__add_nickname_to_users.sql
alter table users add column nickname varchar(30);
```

Line by line:

- `ddl-auto: validate`: Hibernate never writes DDL. It only fails fast if an entity references something the migrations didn't create.
- `V1__create_users.sql`: Flyway's naming rule is `V<version>__<description>.sql`, with a **double** underscore. Flyway applies files in version order and records each one in a table called `flyway_schema_history`, so every database (yours, a teammate's, production) ends up with the same schema.
- `V2__...`: A schema change is a **new file**. You never edit a migration that has already been applied. Flyway stores a checksum for each file and refuses to start if an applied file has changed.
- Spring Boot runs Flyway **before** Hibernate initializes. That ordering is what makes `validate` work: the tables exist by the time Hibernate checks them.

Now the rename case from earlier is handled properly, because you write the intent yourself:

```sql
-- V3__rename_name_to_full_name.sql
alter table users rename column name to full_name;
```

That is a rename that keeps the data, which `update` could never do.

## Per-environment configuration

```yaml
# application-dev.yml (disposable local database, no Flyway yet)
spring:
  jpa:
    hibernate:
      ddl-auto: create-drop
    show-sql: true
```

```yaml
# application-test.yml
spring:
  jpa:
    hibernate:
      ddl-auto: create-drop
```

```yaml
# application-prod.yml
spring:
  jpa:
    hibernate:
      ddl-auto: none
```

- `dev` with `create-drop`: Fine for the first hours of a prototype. Move to Flyway as soon as the schema matters to you.
- `test` with `create-drop`: Tests need a clean schema each run. Note that tests on H2 don't prove the schema works on PostgreSQL, since dialect differences are real. A real-database test (Testcontainers) with the same Flyway migrations as production is better.
- `prod` with `none` (or `validate`): The application should not be able to alter the schema as a side effect of starting up.

## Edge cases and related details

- **Generating a first migration draft:** You can ask Hibernate to write the DDL to a file instead of running it, then paste the result into `V1__...sql` and review it:
    
    ```yaml
    spring:
      jpa:
        properties:
          jakarta.persistence.schema-generation.scripts.action: create
          jakarta.persistence.schema-generation.scripts.create-target: build/create.sql
    ```
    
    Generated SQL is a starting point, not something to ship unreviewed.
    
- **Naming mismatches break `validate`:** Spring Boot's default naming strategy converts `fullName` to `full_name`. If your migration says `fullname`, validation reports a missing column.
    
- **`schema.sql` / `data.sql`:** Spring Boot's own SQL init (`spring.sql.init.*`) is a separate mechanism from Hibernate's `ddl-auto`. By default `data.sql` runs _before_ Hibernate creates tables, so inserts fail. `spring.jpa.defer-datasource-initialization=true` flips the order. Another reason to use Flyway rather than mixing the two.
    
- **Permissions:** In production, the database user your app connects with should not have rights to drop or alter tables. Run migrations with a separate, more privileged user. Then even a misconfigured `ddl-auto` cannot destroy data.
    
- **`spring.jpa.generate-ddl`:** A boolean in Spring's own JPA layer that is roughly "update or none". Prefer the explicit `ddl-auto` property so you can see exactly which mode you're in.
    

## Alternatives to `ddl-auto` for managing the schema

- **Flyway**: plain SQL files, simple, the common default in Spring Boot projects.
- **Liquibase**: changelogs in XML/YAML/SQL, with more features like rollback definitions and database-independent change types, at the cost of more complexity.
- **Hand-run SQL scripts**: no history, easy to forget which ones ran on which database, and not recommended beyond a throwaway project.

**Rule of thumb:** Hibernate generates schema only for databases you're willing to throw away. Anything with data you care about gets versioned migrations, and Hibernate's role shrinks to `validate` or `none`.
