

## 1. Mental model

Every entity needs a **primary key**. `@GeneratedValue` says: "don't make me assign the ID myself, someone else generates it." The `strategy` decides **who** generates it and **when**.

Think of a ticket system at a deli counter:

- **IDENTITY**: the database hands you the ticket only when you walk in (on INSERT).
- **SEQUENCE**: you ask a ticket machine (a DB sequence) for numbers _before_ going in, and can grab several at once.
- **TABLE**: the numbers are written in a ledger book (a table) that everyone must lock, read, update.
- **UUID**: you invent a globally unique random name yourself, no counter needed.
- **AUTO**: "you pick for me."

```java
@Entity
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
}
```

The annotation has two parameters: `strategy` (a `GenerationType` enum) and `generator` (a name linking to a custom generator definition, used mainly with SEQUENCE/TABLE).

---

## 2. The strategies

### `GenerationType.IDENTITY`

- **What:** Uses the database's auto-increment column. On PostgreSQL, Hibernate creates the column as `bigint generated by default as identity`.
- **Example:**
    
    ```java
    @Id@GeneratedValue(strategy = GenerationType.IDENTITY)private Long id;
    ```
    
- **How it works:** The ID does not exist until the INSERT runs. So when you call `repo.save(entity)`, Hibernate **must execute the INSERT immediately** to learn the ID.
- **Why use it:** It is simple, and the table can also be filled by plain SQL or other tools.
- **Gotchas:**
    - **Disables JDBC batching** for inserts, because each insert must go out immediately. This is the one I mentioned earlier.
    - It breaks Hibernate's "delay writes until commit" optimization for new entities.

### `GenerationType.SEQUENCE`

- **What:** Uses a database sequence object. PostgreSQL has them natively.
- **Example (basic):**
    
    ```java
    @Id@GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "user_seq")@SequenceGenerator(name = "user_seq", sequenceName = "user_seq", allocationSize = 50)private Long id;
    ```
    
- **Parameters of `@SequenceGenerator`:**
    - `name`: the label that `generator` refers to.
    - `sequenceName`: the actual sequence in the database.
    - `allocationSize`: how many IDs Hibernate reserves per database call. **Default 50.**
    - `initialValue`: the starting number.
    - `schema` / `catalog`: where the sequence lives.
- **How it works (the pooled optimizer):** Hibernate asks the sequence for a value, say 1000, and **assumes it can hand out the next 50 IDs in memory** (951-1000, depending on the optimizer) without asking again. So 50 saves cost one trip to the DB for the ID, not 50.
- **Why use it:** The ID is known **before** the INSERT, so Hibernate can batch inserts and delay them until flush. It is the best choice for PostgreSQL in most cases.
- **Gotchas:**
    - **`allocationSize` must match the sequence's `INCREMENT BY`.** If Hibernate thinks 50 but the DB sequence increments by 1, Hibernate gets confused and produces duplicate or overlapping IDs. With Flyway-managed schemas, write `CREATE SEQUENCE user_seq INCREMENT BY 50;`.
    - IDs have **gaps** after restarts (the unused part of a reserved block is lost). That's harmless, but don't expect gap-free IDs.
    - Multiple apps inserting with raw SQL need to use `nextval` carefully because of the increment.

### `GenerationType.TABLE`

- **What:** Simulates a sequence using a separate table that stores the next value.
- **Example:**
    
    ```java
    @Id@GeneratedValue(strategy = GenerationType.TABLE, generator = "id_gen")@TableGenerator(name = "id_gen", table = "id_generator",                pkColumnName = "gen_name", valueColumnName = "gen_value",                pkColumnValue = "user", allocationSize = 50)private Long id;
    ```
    
- **How it works:** Hibernate locks a row in the table, reads the counter, increments it, commits.
- **Why it exists:** It is a fallback for databases with neither sequences nor auto-increment.
- **Gotchas:** It is **slow** because of row locking and extra transactions, and it does not scale well. Avoid it with PostgreSQL, since you have better options.

### `GenerationType.UUID` (JPA 3.1+, Spring Boot 3)

- **What:** Generates a random 128-bit UUID in Java.
- **Example:**
    
    ```java
    @Id@GeneratedValue(strategy = GenerationType.UUID)private UUID id;
    ```
    
- **How it works:** Hibernate generates the value in the application with no database round trip. PostgreSQL has a native `uuid` column type.
- **Why use it:**
    - IDs can be created **anywhere**: multiple services, offline clients, merged databases, with no collisions.
    - They don't reveal how many records you have, unlike `/users/1`, `/users/2`.
    - There's no DB trip, so batching works.
- **Gotchas:**
    - Random UUIDs (v4) are **not ordered**, so inserts scatter across the B-tree index. That causes page splits and a bigger, slower index on large tables. Time-ordered UUIDs (v7) fix this, and newer Hibernate versions offer them through `@UuidGenerator(style = UuidGenerator.Style.TIME)`.
    - They take 16 bytes instead of 8 for a `bigint`, and they are harder to read in logs.

### `GenerationType.AUTO` (the default)

- **What:** Lets the persistence provider choose based on the ID's Java type and the database.
- **Example:**
    
    ```java
    @Id@GeneratedValue   // same as strategy = AUTOprivate Long id;
    ```
    
- **What Hibernate 6 actually does:** For `Long`/`Integer`, it chooses **SEQUENCE**. For `UUID`, it generates a UUID. On PostgreSQL it will create a sequence named `<entity>_seq` with `allocationSize` 50.
- **Why/Gotcha:** It is convenient, but it **changed behavior between Hibernate 5 and 6**. In Hibernate 5 it often picked a shared global `hibernate_sequence`. If you upgrade, or read old tutorials, this causes surprise schema mismatches. Be explicit in real projects.

---

## 3. Comparison

|Strategy|Who generates|ID known before INSERT|Batching|Best for|
|---|---|---|---|---|
|IDENTITY|Database (auto-increment)|No|Disabled|Simple apps, small tables|
|SEQUENCE|Database sequence|Yes|Works|**PostgreSQL default choice**|
|TABLE|Separate table|Yes|Works (slow)|Legacy DBs without sequences|
|UUID|Java (Hibernate)|Yes|Works|Distributed systems, public IDs|
|AUTO|Hibernate decides|Depends|Depends|Prototypes|

## 4. Connection to `application.properties`

Tying this back to the previous guide:

```properties
spring.jpa.properties.hibernate.jdbc.batch_size=50
spring.jpa.properties.hibernate.order_inserts=true
```

These only deliver the speedup with SEQUENCE or UUID. With IDENTITY they are silently ignored for inserts. And with `ddl-auto=validate` plus Flyway, your migration must create the sequence with a matching increment:

```sql
CREATE SEQUENCE user_seq START WITH 1 INCREMENT BY 50;
CREATE TABLE users (id BIGINT PRIMARY KEY, name VARCHAR(100));
```

---

## 5. Which one should you pick?

- **Learning / small CRUD app:** IDENTITY is fine and the easiest to understand.
- **Real PostgreSQL app with bulk inserts:** SEQUENCE with `allocationSize` matching the DB.
- **Exposed IDs, microservices, merging data:** UUID (prefer time-ordered).
- **Avoid:** TABLE, and AUTO in anything serious.

A related edge case: assigning IDs yourself (no `@GeneratedValue`) makes Spring Data's `save()` treat an entity with a non-null ID as existing. It then runs a `SELECT` first to decide between insert and merge, which is a hidden cost. Implementing `Persistable<ID>` solves that.
