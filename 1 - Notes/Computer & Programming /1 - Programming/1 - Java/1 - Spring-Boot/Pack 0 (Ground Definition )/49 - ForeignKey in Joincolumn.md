

`@JoinColumn` tells JPA which column holds the link between two tables. Its `foreignKey` attribute goes one step further: it tells JPA how the database's **foreign key constraint** on that column should look. That means the constraint's name, whether it exists at all, and optionally its exact SQL. You fill it with another annotation, `@ForeignKey`.

One thing matters before anything else: this attribute only affects the schema that **Hibernate generates**. At runtime it changes nothing about how your queries or saves behave. In production you normally create tables with Flyway (your DDL lesson), so this attribute is mostly about naming and dev/test setups. The sections below show exactly when it does something and when it doesn't.

## What the attribute looks like

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(
    name = "order_id",
    nullable = false,
    foreignKey = @ForeignKey(name = "fk_order_item_order")
)
private Order order;
```

This is the owning side from your bidirectional lesson. In a bidirectional relationship, the `mappedBy` side has no `@JoinColumn`, so it has no `foreignKey` either.

`@ForeignKey` (from `jakarta.persistence`, not the old Hibernate one) has three attributes:

|Attribute|What it controls|Default|
|---|---|---|
|`name`|The constraint's name in the database|Hibernate invents one, like `FKm3k9x2v7q8l1...`|
|`value`|A `ConstraintMode`: create the constraint or not|`PROVIDER_DEFAULT` (Hibernate creates it)|
|`foreignKeyDefinition`|Your own SQL for the constraint|none (Hibernate writes it)|

## `name`: use it

Without a name, Hibernate generates a hash-like name. You see it in error messages and in `\d order_item` in psql, and you can't guess it. When an insert fails you read this:

```
ERROR: insert or update on table "order_item" violates foreign key constraint "fk_order_item_order"
```

versus a random string. A readable name also means you can find and drop the constraint in a migration. A simple convention: `fk_<child table>_<parent table>`. PostgreSQL limits identifiers to 63 characters, so keep it short.

## `value`: `ConstraintMode`

It has three values:

- `CONSTRAINT`: always create the foreign key.
- `NO_CONSTRAINT`: do **not** create it. The column exists, but the database doesn't check it.
- `PROVIDER_DEFAULT`: let Hibernate decide (it creates the constraint).

```java
@JoinColumn(name = "order_id", foreignKey = @ForeignKey(ConstraintMode.NO_CONSTRAINT))
```

Be careful with `NO_CONSTRAINT`. Without the constraint, the database allows an `order_item` row whose `order_id` points to an order that doesn't exist. Hibernate then throws `EntityNotFoundException` when it tries to load that parent. The cases where it is justified are rare: data split across databases, a legacy schema you don't control, or very large bulk loads. For a normal production app, keep the constraint. The database is the last line of defense when your code has a bug.

## `foreignKeyDefinition`: your own SQL

```java
foreignKey = @ForeignKey(
    name = "fk_order_item_order",
    foreignKeyDefinition = "FOREIGN KEY (order_id) REFERENCES orders (id) ON DELETE CASCADE"
)
```

You use this to get something JPA has no annotation for, like `ON DELETE CASCADE`. Hibernate uses your text as the constraint's body and does not check it. The syntax is database-specific, so it can break when you switch from PostgreSQL to SQLite. Prefer either Hibernate's `@OnDelete(action = OnDeleteAction.CASCADE)` or writing the constraint in Flyway.

## When it actually runs

Hibernate only reads `foreignKey` when it creates or updates the schema:

|Setup|Does `foreignKey` have effect?|
|---|---|
|`spring.jpa.hibernate.ddl-auto=create` / `create-drop` / `update`|Yes, Hibernate writes the `ALTER TABLE ... ADD CONSTRAINT`|
|`ddl-auto=validate` or `none` (Flyway creates the tables)|No. The database already has whatever your SQL migration created|

So in production, the real foreign key is in your migration:

```sql
CREATE TABLE order_item (
    id       BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    order_id BIGINT NOT NULL,
    CONSTRAINT fk_order_item_order FOREIGN KEY (order_id) REFERENCES orders (id)
);

CREATE INDEX idx_order_item_order_id ON order_item (order_id);
```

The name in `@ForeignKey` should match this name. That keeps your tests (which may use `create-drop`) and production consistent, and it documents the constraint on the entity. If they differ, nothing breaks at runtime, but you now have two names for one constraint.

Look at the `CREATE INDEX` line. **PostgreSQL does not create an index on a foreign key column automatically.** Without one, joins on `order_id` and deleting an order (the database must check that no items still point to it) scan the whole child table. Index every foreign key column you query by. The `indexes` attribute of `@Table` from your last lesson does the same from Java.

## Where else `foreignKey` appears

- `@JoinColumn` on `@ManyToOne` and on `@OneToOne` (the examples above).
- `@JoinColumn` on a unidirectional `@OneToMany`, where the foreign key sits on the child table.
- `@JoinTable` has two: `foreignKey` for the owner side and `inverseForeignKey` for the other side of the link table.
- `@PrimaryKeyJoinColumn` and `@CollectionTable` also accept it.

## Short related concepts

- **`@OnDelete`**: a Hibernate annotation that adds `ON DELETE CASCADE` to the generated foreign key, so the database deletes child rows itself when the parent goes. It's faster than loading and deleting children one by one, but Hibernate's persistence context doesn't know the rows are gone, so use it only on relationships where you don't hold those children in memory.
- **`referencedColumnName`**: another `@JoinColumn` attribute. By default the foreign key points to the parent's primary key. This attribute points it at a different **unique** column, like `email`. Rarely needed, and the primary key is almost always the better target.
- **SQLite**: it doesn't enforce foreign keys unless every connection runs `PRAGMA foreign_keys = ON`. A constraint you declared can be silently ignored there, which is another reason to test your relationships against PostgreSQL.
