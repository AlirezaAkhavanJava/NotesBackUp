

This pattern means an entity carries **two separate identifiers that serve two separate audiences**: an internal, sequential numeric id that the database and JPA use for primary-key work (joins, indexes, foreign keys), and a second, independent UUID column that's the _only_ identifier ever shown outside the application — in URLs, API responses, logs sent to a client, etc. The two never substitute for each other; the numeric id never leaves the backend, and the UUID is never used as the actual `@Id` for relationships.

### The problem this solves

A sequential primary key (`1`, `2`, `3`, ...) is cheap and fast for the database, but terrible to expose externally for two concrete reasons:

- **Enumeration** — if `GET /api/accounts/1042` works, so does `/1043`, `/1041`, `/1`... An attacker (or a competitor) can walk every id and scrape your entire dataset, and the id itself leaks business information (how many accounts you have, growth rate between two dates you sampled).
- **Predictable URLs invite tampering** — even with authorization checks in place, sequential ids make it trivial to _try_ accessing other people's resources, which is exactly the kind of attack surface you don't want to rely on your authorization layer alone to catch.

A UUID doesn't have this problem — `3f2504e0-4f89-11d3-9a0c-0305e82c3301` tells an outsider nothing and can't be incremented into someone else's resource. So the obvious move seems to be: make the UUID the primary key. That introduces a different, purely performance-driven problem.

### Why UUID shouldn't just replace the numeric PK

A `BIGINT` primary key generated by a sequence is **monotonically increasing** — each new row's key is larger than the last. B-tree indexes (which is what your primary key index is) love this: every insert appends to the right-hand edge of the index, which is cheap and keeps the index physically well-organized.

A random UUID (the common `UUIDv4`) has none of that structure — each new value lands at a random point in the index's key space. Every insert forces the database to split and rebalance pages all over the index rather than appending at the edge, which fragments the index over time and measurably slows down inserts as the table grows. On top of that, `UUID` is 16 bytes versus 8 bytes for a `BIGINT` — every foreign key column referencing this table, and every index entry, is now twice the size, which adds up once you have `Orders.account_id`, `Orders.id` referenced elsewhere, and so on.

So: good for external safety, bad for internal performance. The dual-identifier strategy keeps both properties by **not making them the same column**.

### Entity design

```java
@Entity
@Table(
    name = "account",
    uniqueConstraints = @UniqueConstraint(columnNames = "public_id")
)
public class Account {

    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "account_seq")
    @SequenceGenerator(name = "account_seq", sequenceName = "account_id_seq", allocationSize = 50)
    @Column(name = "id")
    private Long id;

    @Column(name = "public_id", nullable = false, updatable = false)
    private UUID publicId = UUID.randomUUID();

    private String email;

    // getters/setters
}
```

Two things worth noticing here, since they're new compared to what you've already covered on `@GeneratedValue`/`@SequenceGenerator`:

- `publicId` has **no** `@GeneratedValue` — it's not a JPA-managed id at all, just a normal column. Assigning it with a field initializer (`= UUID.randomUUID()`) means the value exists the instant the object is constructed in Java, before it's ever sent to the database — unlike `id`, which stays `null` until the `INSERT` happens (or until the sequence is pre-fetched, if you're using `allocationSize` optimizations you've already learned).
- `updatable = false` on `publicId` isn't decorative — it tells Hibernate to never include this column in an `UPDATE` statement, which matches the intent: once assigned, a public id should never change, because external systems (bookmarks, other services, logs) may have already captured it.

### Letting the database generate the UUID instead

If you'd rather the UUID come from the database (useful if rows can also be inserted outside your Spring app — a migration script, another service writing directly to the table), Postgres can generate it at the column-default level:

```sql
public_id UUID NOT NULL DEFAULT gen_random_uuid()
```

With this, you'd map `publicId` with `insertable = false` is _not_ what you want (that would stop Hibernate from sending it at all, which is fine) — more precisely, you'd leave the field unset in Java and let `@Column(name = "public_id", updatable = false, insertable = false)` tell Hibernate "don't send a value, just read back whatever the database assigned after insert." Which of the two approaches (Java-generated vs. DB-generated) you pick is mostly a question of whether non-JPA writers exist; if everything goes through your entities, generating it in Java is simpler and keeps the value visible immediately after `new Account(...)`, without needing a refresh from the database.

### Using the two ids

The rule that makes this pattern actually work is: **internal code uses `id`, anything facing outside the backend uses `publicId`** — no exceptions, or the whole point of hiding the sequential id is defeated.

```java
public interface AccountRepository extends JpaRepository<Account, Long> {
    Optional<Account> findByPublicId(UUID publicId);
}

@RestController
@RequestMapping("/api/accounts")
@RequiredArgsConstructor
class AccountController {

    private final AccountRepository accountRepository;

    @GetMapping("/{publicId}")
    public AccountDto getAccount(@PathVariable UUID publicId) {
        Account account = accountRepository.findByPublicId(publicId)
                .orElseThrow(() -> new AccountNotFoundException(publicId));
        return AccountMapper.toDto(account); // DTO exposes publicId, never id
    }
}
```

The URL path variable is typed as `UUID`, not `Long` — Spring will 400 automatically on anything that isn't a valid UUID, which is a free bit of input validation you don't get with a bare numeric path variable. Internally, `@ManyToOne` associations (like your `Orders → Account` link) still use `id` for the actual foreign key column — that part of your schema doesn't change at all. The `DTO` your controller returns is where the substitution happens: it carries `publicId` under the field name `id` (or whatever your API contract calls it), and the real numeric `id` never gets serialized into a response.

### Summary of the trade you're making

||Sequential `id` (BIGINT)|`publicId` (UUID)|
|---|---|---|
|Used for|primary key, foreign keys, joins, indexes|API paths, logs, anything external|
|Generated by|DB sequence|app (`UUID.randomUUID()`) or DB default|
|Index behavior|append-friendly, stays compact|random inserts, 2x storage|
|Exposed externally?|never|always, in place of `id`|
