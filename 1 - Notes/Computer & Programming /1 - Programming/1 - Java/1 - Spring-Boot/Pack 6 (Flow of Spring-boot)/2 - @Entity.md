

## Mental model: a blueprint for a database row

Your database stores data in **tables with rows**. Your Java code works with **objects with fields**. These are two different worlds, and something has to translate between them.

An **entity** is a Java class that is **declared to be mirrored by a database table**:

```
Java world                         Database world
──────────                         ──────────────
class Product            ◄────►    table product
object (one instance)    ◄────►    one row
field (name, price)      ◄────►    column
```

`@Entity` is the label that says: _"This class isn't just a Java class. Persist its objects, and give me a table for it."_ Think of it like a **passport photo-booth template**: the class is the template, and each object is one person's photo that gets stored in the archive (the table).

This translation is called **ORM** (Object-Relational Mapping).

## Definition

```java
import jakarta.persistence.*;

@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(precision = 10, scale = 2)
    private BigDecimal price;

    protected Product() { }                    // required by JPA

    public Product(String name, BigDecimal price) {
        this.name = name;
        this.price = price;
    }

    // getters (and setters only where needed)
}
```

This produces roughly:

```sql
CREATE TABLE products (
    id    BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name  VARCHAR(100) NOT NULL,
    price NUMERIC(10,2)
);
```

## What an entity depends on (the real question)

An entity is not self-sufficient. It depends on **five layers**, from top to bottom:

```
Your @Entity class
     
 ▲ read by

JPA API (jakarta.persistence: the annotations and rules, just a specification)
     
 ▲ implemented by

Hibernate     (the "JPA provider": the engine that does the work)
      
      ▲ talks through

Spring Data JPA  (EntityManager, repositories, transactions)
      
      ▲ uses

JDBC driver + connection pool (HikariCP) + DataSource
      
      ▲ connects to

The database     (PostgreSQL, MySQL, H2...)

```

### 1. The JPA specification (`jakarta.persistence.*`)

`@Entity`, `@Id`, `@Table`, `@Column` come from **JPA**, which is only a _contract_, a set of interfaces and annotations. Alone it does nothing.

> **Spring Boot 3 gotcha:** the package is `jakarta.persistence`, not `javax.persistence`. Old tutorials use `javax`, and that import won't compile in Boot 3 (Java EE moved to Jakarta EE).

### 2. A JPA provider: Hibernate

Someone must **implement** the contract. Hibernate reads your annotations, generates SQL, and fills objects from result sets. Spring Boot includes it by default.

### 3. Spring Data JPA

Wires Hibernate into Spring: it creates the `EntityManager`, manages transactions, and gives you `JpaRepository<Product, Long>`.

### 4. JDBC driver + DataSource

Hibernate produces SQL, but sending it to the database requires the **driver** for that specific database and a **connection pool** (HikariCP, included in Boot).

### 5. A real database, plus configuration

**Dependencies (Maven):**

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-jpa</artifactId>   <!-- JPA + Hibernate + Spring Data + Hikari -->
</dependency>
<dependency>
    <groupId>org.postgresql</groupId>
    <artifactId>postgresql</artifactId>                     <!-- the driver -->
    <scope>runtime</scope>
</dependency>
```

**`application.properties`:**

```properties
spring.datasource.url=jdbc:postgresql://localhost:5432/shop
spring.datasource.username=shop_user
spring.datasource.password=change-me
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.show-sql=true
```

For learning on Debian, the fastest start is **H2** (an in-memory database, no installation: add the `h2` dependency and omit the `datasource` lines). Later move to PostgreSQL (`sudo apt install postgresql`).

**What if you don't have these?**

|Missing|Result|
|---|---|
|`starter-data-jpa`|`@Entity` doesn't even compile (`jakarta.persistence` not found)|
|JDBC driver|Startup fails: _"Failed to determine a suitable driver class"_|
|DB not running or wrong URL/password|Startup fails: connection refused / authentication failed|
|`@Id` on the class|Startup fails: _"No identifier specified for entity"_|

## Rules an entity must follow (and why)

|Rule|Why it works this way|
|---|---|
|Must have an **`@Id`**|Hibernate needs to tell rows apart: update _this_ row, not another|
|Must have a **no-arg constructor** (`public` or `protected`)|Hibernate creates empty objects via reflection, then fills fields from the row|
|Class must **not be `final`**, no `final` persistent fields|Hibernate creates **proxy subclasses** for lazy loading; `final` blocks subclassing|
|Therefore a Java **`record` cannot be an entity**|Records are final with no no-arg constructor. Use records for DTOs, and entities as classes|
|Fields should be non-`public`|Hibernate intercepts access to detect changes|

**Where the annotations sit decides the "access type":** annotating a **field** (`@Id` on `id`) means Hibernate reads fields directly. Annotating a **getter** means it uses getters. Pick one and stay consistent. Field access is the modern default.

## The key annotations

```java
@Entity                                   // this class is persistent
@Table(name = "products",                 // table name (default: class name, snake_cased by Boot)
       uniqueConstraints = @UniqueConstraint(columnNames = "sku"),
       indexes = @Index(columnList = "name"))
public class Product {

    @Id                                   // primary key
    @GeneratedValue(strategy = GenerationType.IDENTITY)   // DB generates it
    private Long id;

    @Column(name = "product_name", nullable = false, length = 100, unique = false)
    private String name;

    @Enumerated(EnumType.STRING)          // store "ACTIVE", NOT the ordinal 0
    private Status status;

    @Transient                            // NOT persisted
    private int cachedScore;

    @Version                              // optimistic locking counter
    private Long version;

    @CreationTimestamp                    // Hibernate-specific
    private Instant createdAt;
}
```

|Annotation|Purpose|If you omit it|
|---|---|---|
|`@Table`|custom name, constraints, indexes|table named after the class (Boot converts `OrderItem` to `order_item`)|
|`@Column`|column name, nullability, length|defaults: nullable, `VARCHAR(255)`|
|`@Enumerated(STRING)`|store enum by name|default is **ORDINAL** (stores 0, 1, 2); inserting a new enum value in the middle silently **corrupts all existing data**|
|`@Transient`|skip a field|Hibernate tries to create a column for it|
|`@Version`|detect concurrent edits|two users overwrite each other (lost update)|

### Identity generation strategies

|Strategy|How the id is made|Notes|
|---|---|---|
|`IDENTITY`|database auto-increment|simple; id known only **after** the INSERT, so Hibernate **can't batch inserts**|
|`SEQUENCE`|a database sequence|best performance; supports batching; the default choice on PostgreSQL/Oracle|
|`AUTO`|Hibernate decides|in Hibernate 6 it picks sequence|
|`UUID`|generated in Java|unguessable (the earlier URL-design point) and generated before saving|
|none|you assign it yourself|for natural keys|

## How an entity lives: the lifecycle (the core "why")

An entity object isn't just an object; it moves through **states** managed by a **persistence context** (think of it as a "workbench" holding the objects Hibernate currently tracks, belonging to one transaction):

```
new Product(...)            →  TRANSIENT   (just a Java object, Hibernate doesn't know it)
repo.save(p)                →  MANAGED     (on the workbench; changes are tracked)
transaction ends            →  DETACHED    (off the workbench; no longer tracked)
repo.delete(p)              →  REMOVED     (scheduled for deletion)
```

**Dirty checking is the magic.** Inside a transaction, you don't have to call `save` for updates:

```java
@Transactional
public void rename(Long id, String newName) {
    Product p = repo.findById(id).orElseThrow();   // MANAGED
    p.setName(newName);                            // just change the object
}   // transaction commits → Hibernate compares to its snapshot → issues UPDATE automatically
```

**Why it works:** when the object was loaded, Hibernate kept a snapshot copy. On commit (the **flush**), it compares the object to the snapshot and generates the `UPDATE` only for what changed. This also means entities have a **first-level cache**: asking for the same id twice in one transaction returns the **same object** with one query.

**What if you forget `@Transactional`?** The object is detached immediately, the change is never tracked, and the update silently never happens. This is among the most common beginner bugs.

## How it connects to what you've learned

```
Client JSON ──► @RequestBody ProductRequest (DTO)
                      │ controller → service (maps DTO → entity)
                      ▼
                Product (ENTITY) ──► repository ──► Hibernate ──► SQL ──► database
                      │
                      ▼ service maps entity → DTO
              ProductResponse (DTO) ──► @ResponseBody ──► JSON to client
```

This is exactly why I kept saying "never expose the entity". Now you can see why, in terms of how entities are built:

|Problem if you return an entity directly|Cause|
|---|---|
|Infinite JSON recursion|bidirectional relationships (`User` ↔ `Order`)|
|`LazyInitializationException`|lazy fields load only while the persistence context is open, and Jackson reads them after it closed|
|Leaked columns|the entity has every column (password hash, internal flags)|
|Mass assignment with `@RequestBody`|the client could set `id`, `version`, `role`|

The entity is the **database's shape**, the DTO is the **API's shape**, and they should change independently.

## Which classes become entities? (scanning)

`@SpringBootApplication` makes Spring Boot register `@Entity` classes found in the **main class's package and below**, the same rule as controllers. An entity placed outside it is invisible, with an error at first use like _"Not a managed type"_ or _"Unknown entity"_. Override with:

```java
@EntityScan("com.alireza.shop")
```

In the **package-by-feature** layout, `Product` sits in `product`, next to its repository.

## Relationships (a preview, since they're where entities get tricky)

```java
@Entity
public class Order {
    @Id @GeneratedValue private Long id;

    @ManyToOne(fetch = FetchType.LAZY)      // many orders → one user
    @JoinColumn(name = "user_id")           // the foreign-key column
    private User user;

    @OneToMany(mappedBy = "order", cascade = CascadeType.ALL, orphanRemoval = true)
    private List<OrderItem> items = new ArrayList<>();
}
```

- `@ManyToOne` / `@OneToMany` / `@OneToOne` / `@ManyToMany` mirror the database's foreign keys.
- The side **without** the foreign key uses `mappedBy` to say "the other side owns the relationship".
- `LAZY` means "don't load the related data until it's accessed". `@ManyToOne` and `@OneToOne` default to **EAGER**, which is usually a performance trap, so set `LAZY` explicitly.

I'll teach these properly after repositories.

## Nuances and gotchas

**1. `User` is a reserved word.** `@Entity class User` creates a table `user`, which is reserved in PostgreSQL and fails with a SQL syntax error. Use `@Table(name = "users")`. Same for `Order` (`ORDER BY`), so use `orders`.

**2. `ddl-auto` is a loaded gun.**

|Value|Effect|
|---|---|
|`none`|do nothing (default for real databases)|
|`validate`|check that the schema matches the entities, and fail on a mismatch|
|`update`|alters tables to match: **can't drop or rename columns**, and is unpredictable|
|`create`|drop and recreate every start|
|`create-drop`|the same, and drop on shutdown (the default for embedded H2)|

`create` against a real database **deletes your data**. In production, use `validate` plus migrations managed by **Flyway** or **Liquibase**, which version your schema changes like Git.

**3. `equals` / `hashCode` are tricky.** Don't use Lombok's `@Data` on entities: it includes all fields (including lazy collections, causing loops and surprise queries) and makes `hashCode` change after `save` assigns the id. The safe pattern is `equals` based on `id` (when not null) with a constant `hashCode`, or a stable business key.

**4. `toString` and lazy fields.** A `toString` that prints a lazy relationship triggers a query, or a `LazyInitializationException`, even in your logs.

**5. The N+1 query problem.** Loading 100 orders, then touching `order.getUser()` on each, fires **1 + 100** queries. The fixes are `JOIN FETCH` or `@EntityGraph`. Watch `show-sql` to catch it.

**6. `open-in-view`.** Spring Boot defaults to `spring.jpa.open-in-view=true`, which keeps the persistence context open through the controller (hiding lazy-loading errors but holding a DB connection longer). Many teams set it to `false` and use DTOs, which forces correct design.

**7. `save()` does both insert and update.** For a new object (null id) it inserts; for an existing id it merges. It also returns the managed instance, so use the return value (`Product saved = repo.save(p)`), not the original.

**8. Entities are not Spring beans.** You create them with `new`. Don't `@Autowired` into them, and don't put business logic that needs services inside them.

**9. Use wrapper types for ids and nullable columns.** `Long id`, not `long`: a primitive can't be `null`, so Hibernate can't tell "new, unsaved" from "id 0".

**10. `@Entity` vs similar annotations.**

|Annotation|Meaning|
|---|---|
|`@Entity`|has its own table and identity|
|`@Embeddable`|a value object **embedded into** another entity's table (e.g. `Address` columns inside `users`); no id of its own|
|`@MappedSuperclass`|shared fields for entities (`id`, `createdAt`) but is not itself a table|
|`@Document` (Spring Data MongoDB)|the equivalent for MongoDB, a different technology|

## Quick reference

|Question|Answer|
|---|---|
|What is it?|a class whose instances are persisted as rows|
|Which package?|`jakarta.persistence` (Boot 3+)|
|What does it depend on?|JPA API → Hibernate → Spring Data JPA → JDBC driver + pool → database|
|Required?|`@Entity`, `@Id`, no-arg constructor, non-final class|
|Can it be a record?|No (use records for DTOs)|
|Found how?|scanned from the main class's package and below|
|Returned from controllers?|No, map to a DTO|
