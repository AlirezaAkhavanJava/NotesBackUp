
## Mental model

Imagine you've checked out 100 books from a library. The library caps you at 1,000 cards, and each book is a **scarce resource**. In Java, each book is represented by a tiny slip of paper on your desk: a `FileInputStream` object, 30-ish bytes of heap holding an integer file descriptor.

The janitor (GC) only comes when your **desk** is full of paper. Your desk is 16 GB, and the slips are tiny, so the janitor doesn't show up for hours. Meanwhile the library (the OS) refuses to lend you a 1,001st book: `Too many open files`.

Three separate things are wrong in that picture:

1. **The janitor watches the wrong gauge.** GC measures heap pressure, not file-descriptor, socket, or native-memory pressure.
2. **The janitor has no schedule.** He may come in a second, an hour, or never (when the JVM exits).
3. **The janitor can't return a book properly.** Returning needs the right person at the right time (flush before close, unlock on the owning thread, send a protocol goodbye). He can only sweep the paper slip.

## Why GC can't do this job

**GC reclaims memory when memory is scarce.** Collections trigger on allocation failure or occupancy thresholds. An object holding a native resource is usually small on the heap and huge, or scarce, outside it. `ByteBuffer.allocateDirect(512 MB)` costs about 100 bytes of heap, so GC sees "nothing worth collecting."

The JDK itself hits this. When the direct-memory limit is reached, the allocation path falls back to calling `System.gc()` and waiting, hoping unreachable buffers get cleaned. That is a hack, and it breaks if someone runs with `-XX:+DisableExplicitGC`.

**Unreachable isn't the same as finished, in either direction.**

- _Finished but still reachable:_ the stream is logically done but stuck in a cache or listener list, so it never becomes garbage and the resource leaks.
- _Unreachable but not cleaned:_ the object is garbage but nobody told the OS.

**Generations make it worse.** If the handle survived a few young collections, it sits in the old generation, which may not be collected until a full or mixed GC, which can be hours away on a healthy heap.

**Cleanup has thread and ordering requirements GC can't know.**

- A lock must be released by the owning thread, but any cleanup runs on some other thread.
- A `BufferedOutputStream` must flush _before_ the underlying stream closes.
- A database transaction should roll back on the connection's thread.
- A GC-driven cleanup has no ordering guarantees between objects dying in the same cycle.

**Memory is the only resource where "later" is nearly free.** That's why a non-deterministic collector works for memory and fails for everything else.

## Finalization: the original (broken) attempt

```java
class Conn {
    @Override protected void finalize() throws Throwable {
        try { closeSocket(); } finally { super.finalize(); }
    }
}
```

**Lifecycle of a finalizable object:**

```
alive → unreachable → queued for finalization → finalize() runs on the
"Finalizer" thread → (still unreachable?) → memory reclaimed at a LATER GC
```

Mechanically:

1. If a class overrides a non-empty `finalize()`, the JVM registers each new instance with a `Finalizer` reference at allocation time, which is a slower allocation path.
2. When GC finds the object unreachable, it can't free it yet. The `Finalizer` reference queues it.
3. A single daemon thread drains the queue, calling `finalize()` on each object.
4. Only if the object is _still_ unreachable after that does a later GC reclaim it.

**Why it was a bad design:**

- **Resurrection.** `finalize()` can store `this` somewhere reachable, bringing the object back to life. The JVM calls `finalize()` at most once per object, so a resurrected object never gets cleaned up again. The lifecycle gets complicated for every GC implementation. Resurrection, plus a measurable performance cost, are among the documented flaws.
- **One thread, no bounds.** A slow or blocked `finalize()` stalls everything behind it. If objects are created faster than they're finalized, the queue grows until `OutOfMemoryError`.
- **Silent failure.** An exception thrown from `finalize()` is swallowed. The object just isn't finalized.
- **Memory retention.** Finalizable objects survive at least one extra GC cycle and are likely promoted to the old generation, so you pay _more_ GC cost for them.
- **No exit guarantee.** At JVM exit, pending finalization usually doesn't run. (The old `runFinalizersOnExit` was removed as unsafe.)
- **`super.finalize()` is manual.** Forget the `try/finally` and the superclass cleanup is skipped.
- **Finalizer attacks.** If a constructor throws (e.g., a security check fails), the half-built object still exists and is eligible for finalization. A malicious subclass can override `finalize()` to resurrect it and use an object that was supposed to be rejected. Mitigations were making `finalize()` `final`, or constructor-time checks, both of which were easy to forget.

**Status:** `Object.finalize()` was deprecated for removal in JDK 18 under JEP 421, and the `--finalization=disabled` flag lets you test your application without it. The plan is staged: deprecate, offer a disable flag, later disable by default, then remove. The JDK is steadily deleting its own `finalize` methods, with another removal in JDK 27. As far as I know, the mechanism itself is not yet removed, so code that relies on it still runs, but don't write new finalizers.

## `Cleaner` (Java 9+): the replacement

**New mental model.** Instead of asking the object to clean up after itself on its deathbed, you register an **undertaker with the will** (just the data needed to release the resource), and the undertaker watches the object from outside. The object is never handed back to anyone, so it can't be resurrected.

```java
public final class NativeBuffer implements AutoCloseable {
    private static final Cleaner CLEANER = Cleaner.create();   // share one per library

    // Must be static and must NOT reference the NativeBuffer instance
    private static final class State implements Runnable {
        private final long address;
        State(long address) { this.address = address; }
        @Override public void run() { freeNative(address); }
    }

    private final long address;
    private final Cleaner.Cleanable cleanable;

    public NativeBuffer(int size) {
        long addr = allocateNative(size);        // acquire first
        this.address = addr;
        this.cleanable = CLEANER.register(this, new State(addr));  // then register
    }

    @Override public void close() { cleanable.clean(); }   // deterministic path
}
```

**How it works underneath:**

1. `register(obj, action)` creates a `PhantomReference` to `obj` and links it into the Cleaner's registry.
2. A daemon thread belonging to the Cleaner blocks on a `ReferenceQueue`.
3. When GC determines `obj` is phantom-reachable, it enqueues the reference.
4. The thread wakes up and runs `action`.
5. `cleanable.clean()` runs the action **at most once** and unregisters it, no matter whether the explicit call or the GC path gets there first. That lets `close()` and the safety net coexist.

**Why phantom references fix resurrection:** a `PhantomReference.get()` always returns `null`. The cleaning code can never reach the dead object, so it can't revive it. (Since Java 9, phantom references are also cleared automatically when enqueued, so the referent's memory isn't held longer.)

**The golden rule: the cleaning action must not strongly reference the object.** The registry holds the action strongly. If the action references the object, the object is _always_ reachable and cleanup never runs. This is the classic bug:

```java
// BUG: lambda uses this.address, so it captures `this` → object can never die
this.cleanable = CLEANER.register(this, () -> freeNative(this.address));

// FIX: capture a local copy, or use a static nested class (as above)
long addr = this.address;
this.cleanable = CLEANER.register(this, () -> freeNative(addr));
```

**What `Cleaner` fixes vs. finalization:** no resurrection, no per-object `Finalizer` allocation cost, you choose the cleaner (and thread) rather than sharing one global finalizer thread, the cleanup state is explicit, and `clean()` provides idempotent explicit release.

**What it does _not_ fix:** it's still driven by GC reachability. The heap-vs-resource-pressure problem from the start of this answer is unchanged. A `Cleaner` is a **safety net, not a resource-management strategy**.

## The right design

```java
try (NativeBuffer b = new NativeBuffer(1 << 20)) {   // deterministic: primary
    use(b);
}                                                     // close() → cleanable.clean()
```

Primary path: `AutoCloseable` plus try-with-resources, so release is immediate and on the right thread. Backup path: a `Cleaner` for the case where someone forgets. The best libraries also log a warning when the cleaner has to do the work, since that means a caller leaked.

This lesson is baked into the Foreign Function & Memory API: `Arena.ofConfined()` and `Arena.ofShared()` are closed explicitly via try-with-resources, while `Arena.ofAuto()` is GC-managed, and the docs steer you toward the former for anything that matters.

## Edge cases and pitfalls

**An object can be "dead" while its method is still running.** The JIT does liveness analysis: after your method last _reads_ a field of `this`, `this` can be considered unreachable even though the method hasn't returned. If it copied out a raw native address and then makes a long native call, GC and the Cleaner can free the memory mid-use: use-after-free.

```java
long read(int off) {
    try {
        return nativeRead(address, off);          // raw long copied out
    } finally {
        Reference.reachabilityFence(this);        // keeps `this` alive until here
    }
}
```

**The cleaner thread is shared and daemon.** A slow cleaning action delays every other cleanup on that Cleaner. Keep actions short and non-blocking. Since it's a daemon thread, pending cleanups don't run at JVM exit.

**Exceptions in cleaning actions go nowhere useful.** The thread survives, but you get no meaningful report. Catch and log inside the action.

**Registration order matters.** Acquire the resource, then register. If registration itself could fail (e.g., out of memory), release the resource manually. If you register first and acquisition fails, you'll try to free garbage.

**Thread-safety of the action.** The action can run on the Cleaner thread concurrently with your other code. `clean()` is atomic and idempotent, so explicit `close()` racing with GC cleanup is safe. Any _other_ state the action touches must be safe too.

**Don't "fix" leaks with `System.gc()`.** It is only a hint, expensive, and defeated by `-XX:+DisableExplicitGC`. If you need it for correctness, your design is wrong.

**`WeakReference` and `SoftReference` are not substitutes.** They help caches. They give you no hook that runs cleanup code with the right state.

## Comparison

||`finalize()`|`Cleaner`|try-with-resources|
|---|---|---|---|
|Runs when|After GC, eventually|After GC, eventually|Exactly at block exit|
|Can resurrect object|Yes|No (phantom)|n/a|
|Thread|Single global Finalizer|A Cleaner's own daemon thread|Caller's thread|
|Guaranteed|No|No|Yes (unless JVM dies)|
|Per-object cost|Slower alloc, extra GC cycle|Registration + reference|None|
|Status|Deprecated for removal|Supported|Preferred|

## Related concepts

- **Reference types** (strong, soft, weak, phantom) and `ReferenceQueue`: the machinery under both mechanisms.
- **`AutoCloseable` and suppressed exceptions:** the deterministic side, covered in the earlier discussion of unwinding.
- **Direct buffers and `Unsafe`/FFM memory:** the main place where native memory meets GC.
- **Leak detection** (e.g., Netty's `ResourceLeakDetector`): the same phantom-reference idea used to _report_ leaks rather than clean up.
- **`reachabilityFence`:** the escape hatch for JIT liveness.
