
# Java 21 — New Features (LTS Release)

Java 21 (released September 2023) is a **Long-Term Support (LTS)** release — one of the most significant LTS releases since Java 8/11/17, finalizing several major features that had been in preview for multiple versions. You've already encountered several of these mentioned in passing throughout this conversation (virtual threads, pattern matching, sealed classes) — this tutorial defines all of them properly, together.

---

## 1. Virtual Threads (JEP 444) — finalized

Already covered in depth in the threads/concurrency tutorials — the headline feature of Java 21.

```java
Thread.startVirtualThread(() -> {
    System.out.println("Running in a virtual thread");
});

try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 10_000; i++) {
        executor.submit(() -> processRequest());
    }
}
```

**Recap of the problem it solves:** traditional Java threads map 1:1 to expensive OS threads, limiting how many you can run concurrently (thousands, not millions). Virtual threads are lightweight, JVM-managed threads that can scale into the millions — letting you write simple, blocking-style code that still scales like non-blocking code. This was the single most consequential change for server-side Java in years, and it's the reason Spring Boot added `spring.threads.virtual.enabled=true`.

## 2. Pattern Matching for `switch` (JEP 441) — finalized

Already used in the exceptions tutorial — here's the full definition.

**Before:** `switch` could only match exact constant values (`int`, `String`, `enum`).

**Now:** `switch` can match **types**, with automatic casting, and even **deconstruct** objects.

```java
Object obj = "Hello";

String result = switch (obj) {
    case Integer i -> "Integer: " + i;
    case String s -> "String: " + s.toUpperCase();
    case null -> "It's null";
    default -> "Unknown type";
};
```

**Guarded patterns (`when` clauses)** — add extra conditions to a case:

```java
String describe(Object obj) {
    return switch (obj) {
        case Integer i when i > 100 -> "Big integer";
        case Integer i -> "Small integer";
        case String s when s.isEmpty() -> "Empty string";
        case String s -> "String: " + s;
        default -> "Something else";
    };
}
```

**Problem it solves:** eliminates the old `instanceof` + manual cast + `if/else` chain pattern entirely (covered in the exceptions tutorial's "pattern matching in catch blocks" section) — now expressible as a single, exhaustive, readable `switch`.

```java
// Old way
if (obj instanceof Integer) {
    Integer i = (Integer) obj;
    // ...
} else if (obj instanceof String) {
    String s = (String) obj;
    // ...
}

// New way — no manual casting at all
switch (obj) {
    case Integer i -> // i is already an Integer
    case String s -> // s is already a String
}
```

## 3. Record Patterns (JEP 440) — finalized

**Definition:** lets you **destructure** a record directly in a pattern — pulling out its component values in one step, instead of calling accessor methods separately.

```java
record Point(int x, int y) {}

Object obj = new Point(3, 4);

// Destructure directly in the pattern
if (obj instanceof Point(int x, int y)) {
    System.out.println("x=" + x + ", y=" + y); // x and y available directly, no .x()/.y() calls needed
}
```

**With `switch`:**

```java
record Point(int x, int y) {}
record Line(Point start, Point end) {}

String describe(Object shape) {
    return switch (shape) {
        case Point(int x, int y) when x == y -> "Point on the diagonal";
        case Point(int x, int y) -> "Point at " + x + "," + y;
        case Line(Point(var x1, var y1), Point(var x2, var y2)) -> "Line from (" + x1 + "," + y1 + ") to (" + x2 + "," + y2 + ")";
        default -> "Unknown shape";
    };
}
```

**Problem it solves:** without record patterns, working with nested records requires manually calling accessor after accessor (`line.start().x()`, `line.end().y()`) — record patterns let you pull out exactly the nested values you need, in one declarative step, directly in the `case` label.

## 4. Sequenced Collections (JEP 431) — finalized

**Definition:** a new set of interfaces (`SequencedCollection`, `SequencedSet`, `SequencedMap`) that add a consistent way to access the **first and last** elements of any ordered collection, plus get a **reversed view**.

```java
List<String> list = new ArrayList<>(List.of("a", "b", "c"));

list.getFirst();   // "a" — new method, works on ANY List now
list.getLast();      // "c"
list.addFirst("z");   // inserts at the front
list.addLast("y");     // inserts at the end
list.removeFirst();     // removes the first element
list.removeLast();       // removes the last element

List<String> reversed = list.reversed(); // NEW — a reversed VIEW of the list
```

**Problem it solves:** before this, "get the first/last element" or "insert at the front" had wildly inconsistent APIs across different collection types:

```java
// Before Java 21 — inconsistent, type-specific ways to do the same conceptual thing
list.get(0);                    // List — first element
list.get(list.size() - 1);         // List — last element  (verbose and error-prone)
deque.getFirst();                    // Deque — has this already
linkedHashMap.entrySet().iterator().next(); // LinkedHashMap — awkward workaround for "first entry"
```

**Now, every ordered collection** (`List`, `Deque`, `LinkedHashSet`, `LinkedHashMap`, `SortedSet`, etc.) gets the **same** `getFirst()`/`getLast()`/`reversed()` methods, uniformly — directly connecting back to and cleaning up something you noticed in the `List` methods tutorial (`.reversed()` was mentioned there as a "Java 21+" addition — this JEP is exactly where that came from).

```java
LinkedHashMap<String, Integer> map = new LinkedHashMap<>();
map.put("a", 1);
map.put("b", 2);

var firstEntry = map.sequencedEntrySet().getFirst(); // works uniformly on Maps too now
```

## 5. Generational ZGC (JEP 439) — finalized

**Definition:** an upgrade to the **Z Garbage Collector** (a low-pause-time garbage collector) that divides tracked objects into "young" and "old" generations, based on the well-established observation that most objects die young.

```
-XX:+UseZGC -XX:+ZGenerational   (enable this GC mode via JVM flags)
```

**Problem it solves:** garbage collection is a background JVM process reclaiming memory from objects no longer in use (something briefly touched on when we discussed `OutOfMemoryError` in the exceptions tutorial). Older ZGC treated all live objects the same way, which was less efficient than necessary — separating short-lived ("young") objects from long-lived ("old") ones lets the collector focus its effort more precisely, **reducing both pause times and CPU overhead** significantly for many real-world workloads.

**Relevance to you:** this is a JVM-configuration-level feature — you don't write code differently because of it, but it's directly relevant if you ever need to tune a Spring Boot application's memory/GC behavior in production.

## 6. Key Encapsulation Mechanism API (JEP 452) — finalized

**Definition:** a new API in `javax.crypto` for **KEM (Key Encapsulation Mechanism)** — a cryptographic technique for securely establishing a shared secret key between two parties, increasingly important for post-quantum cryptography preparation.

```java
KEM kem = KEM.getInstance("DHKEM");
// ... used for establishing shared secrets in encryption protocols
```

**Relevance:** niche, primarily useful for security-focused applications implementing modern key-exchange protocols — connects to the `javax.crypto` mention in the Java API reference tutorial, but not something typical application code touches directly.

## 7. Unnamed Patterns and Variables (JEP 443, preview) — preview feature

**Definition:** lets you use `_` as a placeholder when you need to match a pattern or catch a value **but don't actually need to use it**.

```java
// Before — forced to name a variable you never use
if (obj instanceof Point(int x, int y)) {
    // only cared about x, but y still needed a name
}

// With unnamed patterns (preview) — explicitly signal "don't care"
if (obj instanceof Point(int x, var _)) {
    System.out.println(x); // y was never bound to anything
}
```

```java
try {
    riskyOperation();
} catch (IOException _) { // don't need the exception object itself
    System.out.println("Something failed");
}
```

**Note:** this was a **preview feature** in Java 21 (finalized later, in Java 22) — worth knowing it exists, but treat it as still-settling if working strictly within Java 21 itself, consistent with the "preview features may still change" caution from the earlier structured-concurrency mention in the exceptions tutorial.

## 8. String Templates (JEP 430, preview) — preview feature

**Definition:** a preview mechanism for embedding expressions directly inside string literals, aiming to replace the awkwardness of manual string concatenation or `String.format()`.

```java
String name = "Alireza";
int age = 25;

// Preview syntax (STR template processor)
String message = STR."Hello \{name}, you are \{age} years old.";
```

**Problem it aims to solve:** `String.format("Hello %s, you are %d years old.", name, age)` requires matching placeholders to arguments positionally, which is error-prone for longer strings; string templates let you write the expression **directly inline** where it belongs.

**Important note:** this feature was **later withdrawn** from the JDK entirely — it did not proceed to Java 22 as originally expected, and Anthropic's own knowledge cutoff means treating any long-term status of preview features with the appropriate caution advised in the reasoning behind checking current JDK release notes, exactly as flagged for structured concurrency earlier. If you rely on this in a real project, verify its current status directly rather than assuming it's stable.

## 9. Structured Concurrency (JEP 453, preview) — preview, already introduced

Already mentioned in the exceptions tutorial — worth restating concretely here in context:

```java
try (var scope = StructuredTaskScope.ShutdownOnFailure()) {
    Future<String> user = scope.fork(() -> fetchUser());
    Future<Order> order = scope.fork(() -> fetchOrder());

    scope.join();           // wait for both
    scope.throwIfFailed();    // propagate any failure

    System.out.println(user.resultNow() + ", " + order.resultNow());
}
```

**Problem it solves:** when you fork multiple related concurrent subtasks (as covered in the `ExecutorService`/`CompletableFuture` tutorials), tracking and cancelling them together as a single unit — so a failure in one automatically cancels the others — is otherwise manual and error-prone. Structured concurrency treats a group of related tasks as one unit with a clear lifetime, making concurrent code's error handling and cancellation far more predictable. Still a **preview feature** as of Java 21 — check current JDK status before relying on it in production.

## Where this closes the loop

Java 21 is genuinely the culmination of nearly every advanced topic in this conversation: **virtual threads** directly answers the concurrency/parallelism tutorials' scaling questions; **pattern matching** and **record patterns** complete the `instanceof`/`switch` evolution mentioned in the exceptions tutorial; and **sequenced collections** directly explains the `.reversed()` method that appeared, seemingly out of nowhere, in the `List` methods tutorial. If you're learning Java fresh today, these aren't "new" features to bolt onto old knowledge — they're simply how modern, idiomatic Java is written, and knowing the "why" behind each (as covered throughout this whole conversation) will make code using them feel natural rather than like unfamiliar syntax.
