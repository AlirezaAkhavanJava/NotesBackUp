

`ALTER` is the DDL command that **changes the definition of an object that already exists**. It is mostly used with tables (`ALTER TABLE`), where you add or remove columns, change types, add constraints, and rename things. But PostgreSQL has an `ALTER` command for almost every object type: indexes, sequences, enum types, views, schemas, databases, roles, and even server settings.

In your DDL lesson, `CREATE` made new objects and `DROP` deleted them. `ALTER` is the middle option: the object keeps its data and its identity, and only its definition changes. In real projects, you will use `ALTER TABLE` all the time, because schemas keep changing after the first release. The important part is not the syntax, which is simple, but **what each change costs**: how long it locks the table, and whether it rewrites all the data. That is what this lesson focuses on.

We use the `employees` table from the DQL lesson:

```sql
CREATE TABLE employees (
    id            serial PRIMARY KEY,
    name          text NOT NULL,
    salary        numeric(10,2),
    department_id int REFERENCES departments(id),
    hired_on      date
);
```

## 1. The shape of ALTER TABLE

```sql
ALTER TABLE employees ADD COLUMN email text;
```

The pattern is always the same: `ALTER TABLE <table> <action>`. You can also chain **several actions in one statement**, separated by commas:

```sql
ALTER TABLE employees
    ADD COLUMN email text,
    ADD COLUMN active boolean NOT NULL DEFAULT true,
    DROP COLUMN hired_on;
```

All actions run in one pass, under one lock. That is better than three separate statements, which would each take the lock again and could each rewrite the table.

Useful options on many commands: `IF EXISTS` (for the table or the column) makes the command do nothing instead of failing, which is handy in scripts you run more than once.

```sql
ALTER TABLE IF EXISTS employees ADD COLUMN IF NOT EXISTS email text;
```

## 2. Working with columns

### Add a column

```sql
ALTER TABLE employees ADD COLUMN phone text;
```

Existing rows get `NULL` in the new column. If you add `DEFAULT`, existing rows get that value:

```sql
ALTER TABLE employees ADD COLUMN active boolean NOT NULL DEFAULT true;
```

`NOT NULL` without a `DEFAULT` fails on a table that already has rows: `column "x" of relation "employees" contains null values`. The new column would be `NULL` in every row, which `NOT NULL` forbids.

### Drop a column

```sql
ALTER TABLE employees DROP COLUMN phone;
```

This is fast, because PostgreSQL only marks the column as dropped. The disk space comes back later, as rows are rewritten. If another object depends on the column (a view, for example), you get `cannot drop column phone because other objects depend on it`. Add `CASCADE` to drop the dependent objects too, but check what depends on it first.

### Rename a column

```sql
ALTER TABLE employees RENAME COLUMN salary TO monthly_salary;
```

The data is untouched. Views and constraints follow the new name automatically, but **your application's SQL does not**, so rename in two steps on a live system.

### Change a column's type (with USING)

Say we have a `bonus` column stored as text:

|id|name|bonus|
|---|---|---|
|1|Ana|100|
|2|Omar|200|
|3|Lina|NULL|

```sql
ALTER TABLE employees
    ALTER COLUMN bonus TYPE numeric(10,2) USING bonus::numeric;
```

Line by line:

- `ALTER COLUMN bonus TYPE numeric(10,2)` says the new type.
- `USING bonus::numeric` tells PostgreSQL **how to convert each existing value**. It is the `::` cast from your earlier lesson, used here as a conversion expression.

Without `USING`, PostgreSQL tries an automatic cast. If none exists, you get:

```
ERROR: column "bonus" cannot be cast automatically to type numeric
HINT: You might need to specify "USING bonus::numeric".
```

If some value cannot be converted (say `'n/a'`), the whole command fails with `invalid input syntax for type numeric: "n/a"` and nothing changes. Handle bad values inside `USING`:

```sql
USING NULLIF(bonus, 'n/a')::numeric
```

`NULLIF(bonus, 'n/a')` returns `NULL` when the value is `'n/a'`, so the cast never sees it.

### Defaults and NOT NULL

```sql
ALTER TABLE employees ALTER COLUMN active SET DEFAULT false;
ALTER TABLE employees ALTER COLUMN active DROP DEFAULT;
ALTER TABLE employees ALTER COLUMN name   SET NOT NULL;
ALTER TABLE employees ALTER COLUMN name   DROP NOT NULL;
```

Changing a default affects **only future inserts**. Existing rows keep their values. `SET NOT NULL` checks every row first and fails if any value is `NULL`.

### Identity columns

```sql
ALTER TABLE employees ALTER COLUMN id ADD GENERATED BY DEFAULT AS IDENTITY;
ALTER TABLE employees ALTER COLUMN id RESTART WITH 1000;
```

The first makes an existing integer column auto-numbered. The second changes the next generated value.

## 3. Working with constraints

```sql
ALTER TABLE employees ADD CONSTRAINT employees_email_key UNIQUE (email);
ALTER TABLE employees ADD CONSTRAINT salary_positive CHECK (salary >= 0);
ALTER TABLE employees ADD CONSTRAINT fk_employees_department
    FOREIGN KEY (department_id) REFERENCES departments(id);
ALTER TABLE employees DROP CONSTRAINT salary_positive;
ALTER TABLE employees RENAME CONSTRAINT employees_email_key TO uq_employees_email;
```

Always give constraints a name (`ADD CONSTRAINT name ...`). Otherwise PostgreSQL invents one, and you will need that name later for `DROP CONSTRAINT`.

If existing rows break the rule, the command fails:

```
ERROR: check constraint "salary_positive" of relation "employees" is violated by some row
```

### NOT VALID: add now, check later

`NOT VALID` adds a `CHECK` or `FOREIGN KEY` constraint that applies to **new and changed rows only**, without scanning the old rows. You verify the old rows afterwards:

```sql
ALTER TABLE employees ADD CONSTRAINT salary_positive CHECK (salary >= 0) NOT VALID;
-- fix any bad old rows here
ALTER TABLE employees VALIDATE CONSTRAINT salary_positive;
```

`VALIDATE CONSTRAINT` scans the table, but with a lighter lock that does not block normal reads and writes. This is the standard way to add constraints to big, busy tables.

### Primary keys

```sql
ALTER TABLE logs ADD PRIMARY KEY (id);
```

A table can have only one primary key. To replace it, drop the old constraint first.

## 4. Changing the table itself

```sql
ALTER TABLE employees RENAME TO staff;
ALTER TABLE staff SET SCHEMA archive;       -- move to another schema
ALTER TABLE staff OWNER TO app_admin;       -- change the owner
```

Renaming does not change the data, but every query that uses the old name breaks. Indexes, constraints and sequences keep their old names unless you rename them too.

## 5. The part that matters: locks and rewrites

Most `ALTER TABLE` forms take an **ACCESS EXCLUSIVE** lock. That is the strongest lock: while it is held, **nothing else can touch the table**, not even a `SELECT`. And there is a second problem: the `ALTER` must first **wait** for every running transaction that uses the table. While it waits, new queries line up _behind_ it. So one `ALTER` stuck behind a long transaction can freeze the whole table for everyone.

Protect yourself by setting a timeout, so the `ALTER` gives up instead of blocking everyone:

```sql
SET lock_timeout = '3s';
ALTER TABLE employees ADD COLUMN phone text;
```

If it cannot get the lock in 3 seconds, it fails with `canceling statement due to lock timeout`, and you simply retry later.

The second cost is a **table rewrite**: PostgreSQL copies every row into a new file. The table stays locked the whole time, so on a big table this can take minutes.

|Change|Rewrites the table?|
|---|---|
|`ADD COLUMN` (no default, or a constant default)|No (PostgreSQL 11 and newer)|
|`ADD COLUMN` with a volatile default like `random()`|Yes|
|`DROP COLUMN`|No|
|`RENAME` (column, table, constraint)|No|
|`TYPE varchar(50)` → `varchar(100)`, or `varchar` → `text`|No|
|`TYPE int` → `bigint`, or text → numeric|Yes|
|Making a length smaller (`varchar(100)` → `varchar(50)`)|No rewrite, but it scans to check every row|
|`SET NOT NULL`|No rewrite, but it scans the table|

Safe patterns for big tables:

**SET NOT NULL without a long scan** (PostgreSQL 12 and newer): first add a check, validate it, then set `NOT NULL`. PostgreSQL sees the validated check and skips its own scan.

```sql
ALTER TABLE employees ADD CONSTRAINT name_not_null CHECK (name IS NOT NULL) NOT VALID;
ALTER TABLE employees VALIDATE CONSTRAINT name_not_null;
ALTER TABLE employees ALTER COLUMN name SET NOT NULL;
ALTER TABLE employees DROP CONSTRAINT name_not_null;
```

**UNIQUE without blocking writes:** build the index first, then attach it.

```sql
CREATE UNIQUE INDEX CONCURRENTLY uq_employees_email ON employees (email);
ALTER TABLE employees ADD CONSTRAINT uq_employees_email UNIQUE USING INDEX uq_employees_email;
```

`CREATE INDEX CONCURRENTLY` does not block writes, and the final `ALTER` is then instant.

### DDL is transactional in PostgreSQL

You can wrap several `ALTER`s in a transaction, and if one fails, all of them roll back:

```sql
BEGIN;
ALTER TABLE employees ADD COLUMN phone text;
ALTER TABLE employees ADD CONSTRAINT phone_len CHECK (length(phone) <= 15);
COMMIT;      -- or ROLLBACK;
```

This is a real advantage of PostgreSQL. Many other databases cannot undo DDL. It also means a half-finished schema change never stays in the database. (Exceptions: `CREATE INDEX CONCURRENTLY` cannot run inside a transaction block.)

## 6. ALTER for other objects

|Command|What it does|
|---|---|
|`ALTER INDEX idx RENAME TO new_idx`|rename an index|
|`ALTER SEQUENCE s RESTART WITH 1000`|change the next value of a sequence|
|`ALTER TYPE mood ADD VALUE 'excited'`|add a value to an enum type|
|`ALTER TYPE mood RENAME VALUE 'sad' TO 'down'`|rename an enum value|
|`ALTER VIEW v RENAME TO v2`|rename or change options of a view|
|`ALTER SCHEMA s RENAME TO s2`|rename a schema|
|`ALTER DATABASE appdb SET timezone = 'UTC'`|set a default setting for one database|
|`ALTER ROLE app WITH PASSWORD '...'`|change a user's password or options|
|`ALTER FUNCTION f(int) RENAME TO g`|rename a function|
|`ALTER SYSTEM SET work_mem = '64MB'`|change a server setting (written to `postgresql.auto.conf`)|

Notes you should know:

- **Enums:** you can add or rename values, but you **cannot remove** one. The new value cannot be used in the same transaction that added it.
- **`ALTER SYSTEM`** only writes the file. Run `SELECT pg_reload_conf();` to apply settings that do not need a restart.
- **`ALTER ROLE ... PASSWORD`** stores the password hashed, but the statement itself can appear in server logs, so be careful where you run it.
- A view's _query_ cannot be edited with `ALTER VIEW`. Use `CREATE OR REPLACE VIEW` for that, as long as the columns stay compatible.

## 7. ALTER in a Spring Boot project

In Spring, it is tempting to let Hibernate change the schema with `spring.jpa.hibernate.ddl-auto=update`. It adds columns and tables, but it never drops or changes anything, it does not know about data conversion, and you cannot review or roll back what it did. For real projects, use `validate` or `none` and write `ALTER` statements yourself as **migrations** (the migration lesson from this chat):

```sql
-- src/main/resources/db/migration/V2__add_email_to_employees.sql
ALTER TABLE employees ADD COLUMN email text;
ALTER TABLE employees ADD CONSTRAINT uq_employees_email UNIQUE (email);
```

Flyway runs files like this in version order, once each, and records them in its history table. Rules:

- **Never edit a migration that already ran.** Flyway compares checksums and refuses to start. Write a new `V3__...` file instead.
- Update the entity at the same time:

```java
@Column(unique = true)
private String email;
```

- With `ddl-auto=validate`, Hibernate only checks that the entity matches the tables, and fails at startup if you forgot a migration. That is a good safety net.

## 8. Common errors

|Error message|Cause|Fix|
|---|---|---|
|`column "x" of relation "t" contains null values`|`SET NOT NULL` or `ADD ... NOT NULL` on existing NULLs|update the NULLs first, or add a `DEFAULT`|
|`column "x" cannot be cast automatically to type y`|type change with no automatic conversion|add `USING x::y`|
|`invalid input syntax for type ...`|an old value does not fit the new type|clean it inside `USING`, e.g. with `NULLIF`|
|`cannot drop column x because other objects depend on it`|a view or constraint uses it|drop the dependents, or use `CASCADE` carefully|
|`check constraint "c" ... is violated by some row`|old rows break the new rule|fix the data, or use `NOT VALID` then `VALIDATE`|
|`column "x" of relation "t" already exists`|the column is already there|use `ADD COLUMN IF NOT EXISTS`|
|`canceling statement due to lock timeout`|could not get the table lock in time|retry when the table is quiet|
|`relation "t" does not exist`|wrong name or schema|check the name, or use `schema.table`|

## Related concept, in short

**Schema migration tools (Flyway, Liquibase)** keep a versioned list of your `ALTER`/`CREATE` scripts and apply them in order on every environment, so development, testing and production always end up with the same schema. They are the safe way to run everything in this lesson in a real project.

## Quick summary

- `ALTER` changes an existing object and keeps its data. `ALTER TABLE` is the one you will use most.
- Chain several actions in one `ALTER TABLE` to take the lock once.
- Changing a column's type usually needs `USING` to say how to convert the old values.
- Always name your constraints, and use `NOT VALID` then `VALIDATE CONSTRAINT` on big tables.
- Most `ALTER TABLE` forms take an ACCESS EXCLUSIVE lock, and some rewrite the whole table. Set `lock_timeout` and know which changes are cheap.
- DDL is transactional in PostgreSQL, so a failed `ALTER` rolls back cleanly.
- Use migrations (Flyway), not `ddl-auto=update`, for real schema changes.
