

## `.gitignore` Pattern Syntax — Complete Reference

You've seen pieces of this scattered across the last few topics — this consolidates every pattern rule into one place, with the edge cases that actually bite people.

---

## Core Intuition First

A `.gitignore` pattern is essentially a **simplified wildcard language** (called "glob" patterns) — not full regex, intentionally simpler. Git compares each line against file/folder paths relative to wherever that `.gitignore` sits, and decides match or no-match.

---

## 1. Basic Wildcards

|Symbol|Meaning|Example|Matches|
|---|---|---|---|
|`*`|Any number of characters (not including `/`)|`*.log`|`app.log`, `error.log` — not `logs/app.log` differently than you'd expect (see directory rules below)|
|`?`|Exactly one character|`temp?.txt`|`temp1.txt`, `tempA.txt` — **not** `temp.txt` or `temp10.txt`|
|`[abc]`|Any one character inside the brackets|`log[12].txt`|`log1.txt`, `log2.txt` — not `log3.txt`|
|`[a-z]`|Any one character in the range|`file[a-z].txt`|`filea.txt` through `filez.txt`|
|`[!abc]`|Any one character **except** these|`file[!0-9].txt`|matches any non-digit version|

---

## 2. Directory vs File Matching — The Trailing Slash Rule

This is the single most important distinction, and the one most people get subtly wrong.

|Pattern|Meaning|
|---|---|
|`build`|Matches a file **or** a directory named `build`, anywhere|
|`build/`|Matches **only a directory** named `build` — never a file with that exact name|

```gitignore
target/
```

This can only ever match the folder `target`. If you had a plain _file_ (no extension) literally named `target` somewhere, it would **not** be ignored by this pattern — you'd need `target` without the slash for that.

**Why this distinction exists:** Git wants you to be able to express intent precisely. Ignoring "a specific generated build folder" is a different statement than "anything named build, file or folder."

---

## 3. Anchoring — Leading Slash

|Pattern|Meaning|
|---|---|
|`config.properties`|Matches `config.properties` **anywhere** in the repo (any depth)|
|`/config.properties`|Matches `config.properties` **only at the root** of wherever this `.gitignore` lives|

```gitignore
/pom.xml.bak
```

Only ignores a `pom.xml.bak` sitting directly next to this `.gitignore` file — not one nested inside a subfolder.

**Without** the leading slash, a pattern implicitly behaves as if it had `**/` in front of it — meaning "match this name at any depth."

```gitignore
pom.xml.bak
```

is functionally equivalent to:

```gitignore
**/pom.xml.bak
```

---

## 4. Depth Control — Single `*` vs Double `**`

|Pattern|Meaning|
|---|---|
|`logs/*.log`|Matches `.log` files directly inside `logs/` — **not** nested deeper|
|`logs/**/*.log`|Matches `.log` files inside `logs/` at **any** depth, including nested subfolders|
|`**/logs`|Matches a folder named `logs` at **any** depth in the tree|
|`**/logs/**`|Matches everything **inside** any folder named `logs`, at any depth|

```
logs/
├── app.log           ← matched by logs/*.log
└── archive/
    └── old.log         ← NOT matched by logs/*.log, but IS matched by logs/**/*.log
```

This is exactly analogous to the recursive-vs-single-level distinction in shell globbing — `*` stops at one directory level, `**` recurses through all of them.

---

## 5. Negation (`!`) — Un-ignoring

Covered earlier, formalized here with its exact rules:

```gitignore
*.log
!important.log
```

Ignore all `.log` files **except** `important.log`.

### Rule 1: Order matters

Negation only works on patterns **already defined above it**. A negation line has no effect on patterns that appear _after_ it.

### Rule 2: Can't re-include inside an ignored directory

```gitignore
build/
!build/keep.txt
```

**This does NOT work.** Once `build/` (the directory itself) is ignored, Git never descends into it to evaluate anything inside — including negation rules. The fix is to ignore the _contents_, not the folder itself:

```gitignore
build/*
!build/keep.txt
```

Now `build/` itself isn't ignored as a unit, only its contents are (via the wildcard), so the negation for one specific file inside can actually take effect.

---

## 6. Comments and Escaping

```gitignore
# This is a comment — the whole line is ignored by Git
```

If you actually need to ignore a file whose name **starts with `#`** or `!`, escape it with a backslash:

```gitignore
\#notacomment.txt
\!important-file.txt
```

---

## 7. Trailing Whitespace Gotcha

Trailing spaces at the end of a line are **stripped** unless escaped with a backslash — this occasionally causes silent, confusing mismatches if your editor leaves invisible trailing whitespace:

```gitignore
file.txt    
```

(trailing spaces here are ignored by Git — pattern is just `file.txt`)

```gitignore
file.txt\   
```

(backslash before the space preserves it as part of the pattern — rare, but exists for filenames that genuinely include trailing spaces)

---

## 8. Case Sensitivity

Pattern matching's case sensitivity depends on your **filesystem**, not Git itself:

- Debian (ext4, your setup) → **case-sensitive** — `App.java` and `app.java` are different files, and `*.LOG` would **not** match `error.log`
- Windows/macOS default filesystems → case-insensitive, so patterns are more forgiving there

This matters specifically because of the case-sensitivity conflict scenario covered in the errors/conflicts topic — worth remembering these two connect.

---

## 9. Putting It All Together — Realistic Composite Example

```gitignore
# Ignore all logs anywhere
*.log

# But keep this specific one
!critical.log

# Ignore the entire build folder, any depth
**/build/

# Ignore .class files only directly in target/, not nested test fixtures
target/*.class

# Ignore any file starting with "tmp" at the repo root only
/tmp*

# Ignore a single specific character variant
cache-v?.dat
```

---

## 10. Quick Debugging Reference (Tying Back to Earlier Tools)

|Command|Use|
|---|---|
|`git check-ignore -v <path>`|Shows exactly which `.gitignore`/exclude file + line number is responsible for a match|
|`git status --ignored`|Lists what's currently being ignored|
|`git ls-files --others --ignored --exclude-standard`|Explicit list of ignored, untracked files|

---

**One-line summary to remember:**

> `.gitignore` patterns are glob-style, not regex — `*` stays within one directory level while `**` recurses through all of them, a trailing `/` restricts a pattern to directories only, a leading `/` anchors it to that `.gitignore`'s own folder instead of matching at any depth, and negation (`!`) can only resurrect files whose _containing folder_ was never itself fully ignored as a unit.
